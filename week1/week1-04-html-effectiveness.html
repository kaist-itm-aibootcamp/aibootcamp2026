왜 HTML인가

Markdown은 이제 충분하지 않다

Claude에게 무언가를 만들어달라고 할 때, 결과물을 어떤 형식으로 받을지는 우리가 정할 수 있습니다. 원문 저자는 "Markdown은 점점 더 제한적인 형식이 되고 있다"고 말하며, 거의 모든 작업에서 Markdown 대신 HTML만 쓰는 "HTML 맥시멀리스트"가 되었다고 밝힙니다.

원문: claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html — Thariq Shihipar (Anthropic)

HTML이 Markdown보다 나은 다섯 가지 이유

  • 정보 밀도 — 표, CSS로 표현하는 디자인, SVG 일러스트, 인터랙티브 요소까지 한 파일에 담을 수 있습니다.
  • 시각적 명확성 — 100줄 넘는 Markdown은 잘 안 읽히지만, 탭·일러스트·내부 링크가 있는 HTML은 스캔하듯 읽힙니다.
  • 공유 용이성 — 브라우저에서 바로 열리므로, 첨부파일을 열어야 하는 문서보다 실제로 읽힐 확률이 높습니다.
  • 양방향 인터랙션 — 슬라이더·토글을 조작하고, "복사" 버튼으로 결과를 다시 Claude에게 가져올 수 있습니다.
  • 풍부한 컨텍스트 반영 — 파일, 코드, 대화 기록 등 다양한 소스를 그대로 살려 담을 수 있습니다.
정보 밀도 — 원문에서 소개한, HTML 파일 하나가 담을 수 있는 여덟 가지 정보 유형(표·디자인·일러스트·코드·인터랙션·워크플로우·공간 배치·이미지). Markdown 하나로는 이 중 절반도 담기 어렵습니다.
시각적 명확성 — 같은 내용이라도 Markdown은 240줄을 계속 스크롤해야 하지만, HTML은 탭과 카드로 구조화해 스크롤 대신 한눈에 읽을 수 있게 만듭니다.
요즘엔 게재된 논문 요지를 HTML로도 소개합니다 최근엔 그 논문을 소개하는 전용 웹페이지를 별도의 HTML 사이트로 함께 만들어 보여주는 경우가 늘고 있습니다. 예를 들어 스탠퍼드 SALT Lab의 논문 "PrivacyLens"는 PDF와 별개로 salt-nlp.github.io/PrivacyLens 라는 소개 페이지를 두고 있습니다 — 핵심 요지·그림·데모·데이터를 스크롤 한 번으로 훑어볼 수 있어, PDF만 있을 때보다 훨씬 많은 사람이 실제로 읽어보게 됩니다.

① 기획서 · 계획 · 탐색

같은 제안서, 4가지 버전으로 한눈에 비교하기

기획 초기에는 방향을 하나로 정하기보다 여러 버전을 나란히 비교하는 게 유용합니다. 예를 들어 인테리어 시공사가 고객에게 보낼 리모델링 제안서를, 강조점이 다른 4가지 버전으로 동시에 만들어 비교해볼 수 있습니다.

우리 인테리어 시공사가 고객에게 보낼 리모델링 제안서를 4가지 버전으로 만들어줘.
같은 프로젝트 내용을 (1) 가격 데이터 중심 (2) 선택지 비교 중심
(3) 시각화된 비주얼 중심 (4) 진행 로드맵 중심,
이렇게 4가지 스타일로 각각 짧게 만들어서 하나의 HTML 파일 안에 나란히 비교할 수 있게 보여줘.
예시 화면 — 위 프롬프트로 나올 법한 결과 (거실·주방·욕실 리모델링 제안서)

⚖ 인상적이지만 세부 사양은 생략

② 문서 비교 · 설명

계약서 수정본, 한눈에 비교하기

개발자가 아니어도 이런 방식은 그대로 씁니다. 계약서 수정본을 받았을 때 어디가 바뀌었는지, 왜 바뀌었는지, 그리고 이게 중요한 변경인지를 색으로 구분해서 보여주는 HTML 페이지를 만들 수 있습니다.

계약서 수정 전/후를 비교하는 HTML 페이지를 만들어줘.
바뀐 부분마다 왜 바뀌었는지 이유를 옆에 설명해주고,
계약에 중요한 영향을 주는 변경은 빨간색으로,
의미 변화 없이 문구만 다듬은 부분은 초록색으로 구분해줘.
예시 화면 — 인테리어 공사 계약서 수정본 비교
제3조 (공사 기간)
시공 기간은 계약일로부터 60일 이내로 한다.
시공 기간은 계약일로부터 90일 이내로 한다.
📌 중요 변경 — 자재 수급 지연을 고려해 기간이 30일 늘어났습니다. 준공 지연 배상 조항에도 영향을 줍니다.
제5조 (대금 지급)
계약금은 총 공사비의 10%로 하며, 계약 체결 시 지급한다.
계약금은 총 공사비의 30%로 하며, 계약 체결 시 지급한다.
📌 중요 변경 — 초기 지불 부담이 커집니다. 서명 전 반드시 확인이 필요합니다.
제7조 (하자보수)
하자보수 기간은 준공일로부터 1년으로 한다.
하자보수 기간은 준공일로부터 1년으로 한다(공용부 마감재 포함).
✅ 그대로 — 보수 기간 자체는 변화 없이, 적용 범위를 명확히 하려고 문구만 보완했습니다.

③ 리포트 · 리서치 · 학습자료

제안서를 하나의 설명 페이지로 정리하기

여러 장에 걸친 제안서를 처음 받은 사람도, 프로젝트 전체 흐름이 한눈에 들어오는 요약 페이지가 있으면 훨씬 빠르게 이해할 수 있습니다.

원문에서 소개된 실제 설명 페이지 예시입니다. 사이드바 목차, 클릭해서 펼치는 단계별 섹션, 탭으로 전환하는 코드 조각, 우측 하단의 "읽은 파일" 목록까지 — 개발자를 위한 예시지만, 아래처럼 사이드바 목차 + 단계별 펼치기 + 관여 팀 그리드로 바꾸면 비개발자 대상 제안서 설명 페이지에도 그대로 적용됩니다.
관련 제안서를 읽고 HTML 설명 페이지 하나로 만들어줘:
프로젝트 전체 진행 흐름을 보여주는 다이어그램,
단계별 핵심 내용에 짧은 설명,
마지막에 "주의할 점" 섹션까지 넣어줘.
예시 화면 — 인테리어 리모델링 프로젝트 전체 흐름

계약 · 착수금 단계에서 총 공사비의 30%를 지급하며, 이 시점부터 계약서상 공사 기간(90일)이 시작됩니다.

여러 팀이 협업하는 프로젝트라면, 각 단계에 어느 팀이 관여하는지 세로로 나열한 그리드로 함께 보여줄 수 있습니다.

팀 \ 단계상담·실측디자인 확정계약·착수금시공준공
디자인팀●●

④ 커스텀 편집 도구

역할 분담용 보드 — 사람과 작업을 좌우로 옮기기

범용 도구 대신, 지금 우리 팀의 사람 수와 작업 목록에 딱 맞는 전용 보드를 그때그때 만들어 쓸 수 있습니다. 아래는 팀원 4명에게 작업 6개를 배분하는 보드입니다 — 화살표 버튼을 눌러 작업을 다른 사람에게 실제로 옮겨보세요.

우리 팀원 4명과 작업 6개를 넣어서, 각 작업을 사람들 사이로
좌우로 옮길 수 있는 역할 분담 보드를 HTML로 만들어줘.
사람 이름 옆에는 귀여운 이모티콘을 붙여줘.
현재 배분 결과를 "Markdown으로 복사"할 수 있는 버튼도 추가해줘.
예시 화면 — 실제로 작업을 옮길 수 있는 역할 분담 보드

이제 여러분 차례

여러분의 보고서 · 계획서 · 과제도 HTML로

이 강의 자료 전체, 그리고 오늘 만든 금융 플래너가 이미 이 방식으로 만들어졌습니다. 앞으로 회사에서 쓸 보고서나 프로젝트 계획서, 학교 과제도 워드·파워포인트 대신 HTML 한 파일로 만들어보세요. 아래 프롬프트를 여러분의 실제 내용으로 바꿔서 사용해보세요.

다음 내용을 바탕으로 [보고서 / 프로젝트 계획서 / 과제]를 HTML 한 파일로 만들어줘.

내용: [여기에 핵심 내용을 붙여넣으세요]

조건:
- 표, 색상, 아이콘 등을 활용해 한눈에 읽히게 구성해줘
- 필요하다면 다이어그램(SVG)이나 체크리스트·탭 같은 인터랙티브 요소를 넣어줘
- 마지막에 "요약" 섹션을 추가해줘

Finish

Markdown 대신, HTML로 생각하기

기획, 문서 비교, 리포트, 역할 분담까지 — HTML 한 파일 안에서 전부 가능합니다. 오늘부터 Claude에게 "HTML 파일로 만들어줘"라고 요청해보세요.
