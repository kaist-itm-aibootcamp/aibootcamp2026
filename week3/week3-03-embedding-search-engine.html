WEEK 3 · STEP 3 — 임베딩 검색엔진 구축

유사 판례 검색엔진 —
산업 표준 아키텍처를 내 손으로

앞 페이지에서 키워드 검색의 한계와 임베딩 검색의 가능성을 확인했습니다. 이번 강의는 임베딩 기반 검색엔진의 전체 아키텍처를 이해하고, Claude Code로 판결문 347건짜리 검색엔진을 실제로 구축합니다.

1

이미 세상이 널리 쓰는 기술입니다

임베딩 유사도 검색은 실험적 기법이 아니라, "글자가 아니라 의미로 찾기"가 필요한 모든 곳에 깔려 있는 산업 표준입니다. 추천 기능은 그 용도 중 하나일 뿐입니다.

전문가의 도구로

📋
KIPRIS 유사 특허 검색내 발명의 설명을 넣으면 표현이 달라도 기술적으로 유사한 선행 특허를 찾아줍니다 — 선행기술조사의 핵심 도구.
⚖️
유사 판례 검색리걸테크 서비스의 "이 판결과 유사한 판례" — 오늘 우리가 만드는 것과 같은 구조입니다. 계약서의 유사 조항 검색도 같은 원리.
🎓
관련 논문 탐색학술 검색 서비스의 관련 논문 추천, 저널의 심사위원 매칭 — 초록 임베딩으로 연구 주제의 이웃을 찾습니다.

일상 서비스의 보이지 않는 부품으로

🔍
검색엔진·사내 문서 검색현대 웹 검색과 노션·드라이브류의 문서 검색은 키워드 매칭에 의미 검색을 결합한 하이브리드로 진화했습니다.
🎧
고객센터·FAQ 매칭문의가 들어오면 표현이 달라도 같은 뜻의 과거 문의·답변을 찾아 상담원(또는 봇)에게 건네줍니다.
📑
표절·중복 탐지논문 표절 검사, 같은 사건을 다룬 중복 기사 묶기 — "지나치게 비슷한 문서"를 찾는 것도 유사도 검색입니다.
📷
사진·소리로 찾기사진으로 상품 검색(구글 렌즈류), 허밍으로 노래 찾기 — 이미지·음성도 임베딩하면 같은 "가까운 이웃 찾기" 문제가 됩니다.
💼
매칭 서비스이력서↔채용공고, 프리랜서↔프로젝트 — 서로 다른 문서 두 종류를 같은 좌표계에 놓고 궁합을 재는 응용입니다.
🤖
AI 챗봇의 검색 부품기업 챗봇이 답변 전에 사내 문서를 찾아오는 단계가 바로 이 검색엔진입니다 — 다음 강의(RAG)에서 다룹니다.
2

전체 아키텍처 — 색인(사전 준비)과 검색(실시간)

검색엔진은 두 개의 국면으로 이루어집니다. 문서를 미리 벡터로 만들어 두는 색인 국면(한 번만)과, 질의가 들어올 때마다 도는 검색 국면(매번)입니다.

임베딩 검색엔진 전체 구성도

위(주황) = 미리 한 번 · 아래(파랑) = 검색할 때마다 ①→⑤ 순서로

벡터 DB는 실제로 이렇게 생겼습니다

"벡터 DB"라는 말이 거창하게 들리지만, 우리 것의 실물은 폴더 하나에 담긴 JSON 파일 347개입니다. 왼쪽이 폴더, 오른쪽이 그중 한 파일을 열어본 실제 내용입니다.

일반적으로는 전용 벡터 DB에 저장합니다

우리는 소규모라 JSON 파일로 충분하지만, 실제 서비스는 대부분 전용 벡터 DB(Pinecone, Chroma, Milvus, PostgreSQL의 pgvector 확장 등)에 저장합니다. 말은 거창해도 안을 들여다보면 "벡터 컬럼이 하나 추가된 표"입니다.

-- 전용 벡터 DB의 실물 ① : 테이블 (PostgreSQL + pgvector 예)
-- rulings 테이블
 id  | 법원        | 사건번호      | 소송결과  | embedding vector(4096)
 ----+--------------+---------------+----------+---------------------------
 1   | 수원지방법원 | 2020가단8667  | 원고일부승 | [-0.0112, -0.0057, 0.0381, …]
 2   | 대구지방법원 | 2024가단138550 | 원고일부승 | [ 0.0093, -0.0141, 0.0208, …]
 3   | 울산지방법원 | 2022가단128995 | 원고패   | [-0.0027,  0.0189, 0.0344, …]
 …   | (총 347행 — 문서 1건 = 1행)
-- 전용 벡터 DB의 실물 ② : 검색 질의 (핵심은 이 한 줄)
SELECT 법원, 사건번호, 소송결과
FROM rulings
ORDER BY embedding <=> [질의 벡터]  -- <=> : 벡터 거리(가까운 순 정렬) 연산자
LIMIT 5;  -- 가장 가까운 5건 = 우리 서버의 ⑥단계와 동일한 일
정리 — JSON 폴더든 전용 벡터 DB든 본질은 "문서 id ↔ 벡터"의 대응표이고, 검색은 "가까운 순 정렬"입니다. 전용 DB의 값어치는 문서가 수십만~수백만 건일 때 이 정렬을 전수 비교 없이 빠르게 해주는 색인 기술에 있습니다. "벡터 DB 도입"이라는 말을 들으면 이 표와 이 한 줄 질의를 떠올리면 됩니다.

다섯 단계를 차례로

1
검색창 — 질의는 자연어 문장

키워드가 아니라 "회사가 알고도 방치한 사건" 같은 문장 그대로. 임베딩이 의미를 잡아주기 때문입니다.

2
백엔드 서버 — 질의를 받는 관문

브라우저는 질의문만 백엔드로 보냅니다. API 키는 백엔드에만 있으므로 사용자에게 노출되지 않고, 호출량도 백엔드에서 통제할 수 있습니다.

3
질의 임베딩 — 문장을 좌표로

백엔드가 임베딩 API를 호출해 질의문의 벡터를 얻습니다. 색인 때와 같은 모델이어야 같은 좌표계에 놓입니다 — 다른 모델이면 유사도가 무의미해집니다.

4
최근접 탐색 — DB에서 가장 가까운 문서 찾기

질의 벡터와 347건 문서 벡터의 코사인 유사도를 계산해 가까운 순으로 정렬합니다. 347건이면 전수 비교로 충분하고, 수백만 건 규모가 되면 전용 벡터 DB(근사 최근접 탐색)가 이 단계를 대신합니다.

5
결과 표시 — 유사도 순 문서 목록

상위 k건의 서지·요약·점수를 브라우저에 돌려주면 끝입니다. KIPRIS 유사 특허 검색의 결과 화면과 본질적으로 같은 출력입니다.

질의 하나의 여행 — 데이터 플로우

사용자가 검색 버튼을 누른 순간부터 결과가 화면에 뜨기까지, 세 주체 사이를 데이터가 이렇게 오갑니다.

데이터 플로우 — "동료 직원에 의한 따돌림(왕따)" 검색의 1초

세로 방향 = 시간 순서 · 상자 안 = 각 주체가 하는 일 · 화살표 위 = 실제로 오가는 데이터

주목할 점 두 가지 — 🔑 키는 ③에서 서버가 붙이므로 브라우저에는 끝까지 등장하지 않고, OpenRouter에는 질의문 한 줄만 갈 뿐 판결문 347건은 내 PC를 떠나지 않습니다. 전체 소요는 1초 안팎이며 대부분이 ③~⑤의 왕복입니다.

3

실습 — 계획서부터 대화로

비개발자가 개발을 시킬 때 가장 좋은 방법은 사양서를 쓰는 것이 아니라 대화를 하는 것입니다. 순서는 넷입니다 — 원하는 것만 서술 → AI가 계획서 작성 → 피드백 주고받기 → 확정된 계획서대로 구현. 코드는 못 읽어도 계획서는 읽고 고칠 수 있기 때문입니다.

준비물: Claude Code 로그인(2주차 1강에서 설치해 둔 그것 — 이번 주부터 본격적으로 씁니다), 작업 폴더의 embeddings_json/ 347개, 그리고 같은 폴더에 OpenRouter 키를 한 줄 저장한 openrouterkey.txt. 작업 폴더에서 claude를 실행합니다.

1
원하는 것만 서술한다 — 기술 용어 없이

무엇을 만들지(what)만 말하고, 어떻게 만들지(how)는 말하지 않습니다. 대신 "바로 코드 쓰지 말고 계획서부터"를 명시합니다.

💬 1단계 — 요구 서술 
나는 개발자가 아니야. 바로 코드를 짜지 말고, 계획서부터 만들어줘.

내가 원하는 것:
- 이 폴더의 embeddings_json/ 안에 판결문 347건의 임베딩 JSON이 있어
- 검색창에 문장으로 질의하면, 의미가 비슷한 판결을 순서대로
  보여주는 검색 서비스를 내 컴퓨터에서 돌리고 싶어
- OpenRouter 키는 이 폴더의 openrouterkey.txt 파일에 저장해 두었어
- 완성되면 내가 직접 켜고 끌 수 있어야 해

계획서에는 무엇을 만드는지, 어떤 순서로 만드는지, 중간에 내가
확인할 지점이 어디인지 넣어줘. 결정이 필요한 것은 나에게 질문해줘.

Claude Code에는 계획 모드(코드를 건드리지 않고 계획만 세우는 모드)도 있어서, 이 지시는 도구의 작동 방식과도 잘 맞습니다.

2
AI가 계획서를 만든다 — 이런 답이 돌아옵니다 (예시)
📋 계획서 v1 (요약)
만들 것 — 내 컴퓨터에서만 돌아가는 판결문 의미 검색 웹페이지: 작은 웹서버 하나 + 검색 화면
진행 순서 — 데이터 통합 파일 → 검색 엔진(화면 없이 먼저 검증) → 웹 화면 → 실행 방법 정리
확인 지점 — 시험 검색 결과를 보여드리고 승인받은 뒤 다음 단계로
질문 3가지 — (a) 검색 비교에 본문 임베딩만 쓸까요, 요약 임베딩과 조합할까요? (b) 화면에 법원·연도 같은 필터를 넣을까요? (c) 질의 임베딩에 쓸 모델을 지정해 주시겠어요?

코드가 한 줄도 없는데도 검토할 수 있는 문서가 생겼습니다. 여기가 비개발자가 프로젝트를 통제하는 지점입니다.

3
피드백을 주고받는다 — 질문에 답하고, 요구를 다듬고
💬 3단계 — 피드백 예시 
계획 좋아. 질문에 답할게.
(a) 본문 임베딩과 요약 임베딩 둘 다 비교해서 높은 쪽으로 순위를 정해줘
(b) 필터는 빼고 검색창만 있는 단순 버전으로 하자
(c) 임베딩 모델은 347건을 만들 때 쓴 qwen/qwen3-embedding-8b를
    그대로 써야 해. 왜 같은 모델이어야 하는지도 계획서에 한 줄 적어줘

추가 요구 두 가지:
- 키는 openrouterkey.txt 파일에서만 읽고, 화면·로그·코드
  어디에도 키 값을 출력하거나 복사해 넣지 마
- 서버에 문제가 생기면 비개발자인 내가 읽을 수 있는
  한국어 안내를 보여줘

이 내용 반영해서 계획서 v2로 확정해줘.

피드백 한 번으로 키 보안·모델 통일 같은 핵심 요구가 계획서에 명문화됐습니다. 왕복은 한두 번이면 충분합니다 — 완벽한 계획서보다 "내가 이해하고 승인한 계획서"가 목표입니다.

1. 무엇을 만드는가

내 컴퓨터에서만 돌아가는 판결문 의미 검색 웹페이지입니다.

  • 브라우저에서 http://localhost:8000 같은 주소를 열면 검색창이 하나 나옵니다.
  • 검색창에 문장을 입력합니다. 예: "상사의 폭언으로 우울증이 생겨 손해배상을 청구한 사건"
  • 입력한 문장을 OpenRouter API로 임베딩(숫자 벡터)으로 바꾼 뒤, 미리 만들어 둔 판결문 347건의 임베딩과 유사도를 계산합니다.
  • 의미가 가까운 순서대로 판결 목록을 보여줍니다. 각 결과에는 법원 · 사건번호 · 선고일 · 소송결과 · 사건 개요 · 유사도 점수가 표시되고, 클릭하면 판결문 전문을 볼 수 있습니다.

인터넷에 공개되는 것이 아니라 내 컴퓨터 안에서만 작동합니다. 외부로 나가는 것은 "검색 문장을 임베딩으로 바꿔달라"는 OpenRouter 요청 하나뿐입니다. 판결문 원문이 통째로 외부에 전송되는 일은 없습니다.

2. 확정된 사항 (질문·답변 결과)
항목결정
검색 비교 기준본문 임베딩 + 요약 임베딩 조합 (두 유사도 중 높은 쪽으로 순위 결정)

문서화 — 코드만 남기지 말고, 기록을 남긴다

서버가 돌기 시작하면 끝난 것 같지만, 하나가 빠졌습니다. 한 달 뒤의 나는 남입니다. 코드는 "무엇을 하는지"만 남기고 "왜 이렇게 했는지"는 남기지 않습니다 — 특히 AI와 대화로 만들면 그 논리가 전부 휘발되는 대화 기록 속에 있습니다. 오늘 §3에서 검토한 계획서, 왕복하며 내린 결정들을 파일로 남겨야 다음에 이어서 일할 수 있습니다.

실무 표준을 1인용으로 — 파일 3 + 1

소프트웨어 업계의 표준은 설계 문서(design doc), 결정 기록(ADR, Architecture Decision Record), 운영 문서(README·runbook)의 세 겹입니다. 1인 프로젝트에서는 이것을 저장소 안의 파일 네 개로 줄이면 충분합니다.

파일담는 것실무 표준으로 치면
PLAN.md만들기 전에 합의한 계획서의 최종본 — 무엇을, 어떤 구조로, 어떤 순서로. §3에서 AI가 써 주고 내가 검토한 바로 그 문서를 파일로 저장설계 문서 (design doc)
DECISIONS.md왜 이렇게 했는지 — 날짜 + 결정 + 이유 + 검토했다가 버린 대안. 항목당 2~5줄, 지우지 않고 아래로만 추가결정 기록 (ADR)
README.md처음 보는 사람이 실행·배포까지 — 필요한 것(파이썬·키), 설치, 실행 명령, 환경변수 목록, 배포 방법, 자주 나는 문제README + runbook
CLAUDE.mdAI가 읽는 문서 — Claude Code가 폴더에서 자동으로 읽는 프로젝트 메모. 폴더 구조, 규칙, 자주 쓰는 명령. 다음 세션의 AI가 맥락을 이어받는 통로팀 온보딩 문서
문서도 코드와 같은 저장소에 — 네 파일 모두 프로젝트 폴더에 두고 코드와 함께 커밋합니다. 코드가 바뀐 시점의 문서를 나중에 그대로 찾을 수 있고, "README만 보고 다른 컴퓨터에서 실행되는가"가 문서 품질의 합격선입니다 — 다음 강의(⑥ Vercel 배포)에서 실제로 시험당하게 됩니다.

프롬프트 두 개 — 만들 때 한 번, 규칙으로 한 번

💬 작업 마무리 문서화 프롬프트 — 서버가 돈 직후에 
오늘 작업을 문서로 남기자. 프로젝트 폴더에 네 파일을 만들어줘.
1. PLAN.md — 우리가 합의한 계획서의 최종본 (실제 구현과 달라진 부분은 반영해서)
2. DECISIONS.md — 오늘 내린 주요 결정을 항목별로: 날짜, 결정, 이유,
   검토했다가 버린 대안. 앞으로 결정이 갈릴 때마다 아래에 추가하는 형식으로.
3. README.md — 이 폴더를 처음 보는 사람이 실행까지 갈 수 있게:
   필요한 것, 설치, 실행 명령, 환경변수 목록(값은 빼고 이름과 용도만),
   자주 나는 문제와 해결.
4. CLAUDE.md — 다음 세션의 네가 읽을 프로젝트 메모: 폴더 구조,
   지켜야 할 규칙, 자주 쓰는 명령.
전부 코드에서 확인되는 사실만 쓰고, 확실하지 않은 것은 [확인 필요]로 표시해줘.
💬 유지 규칙 프롬프트 — 문서가 낡지 않게 
CLAUDE.md에 다음 규칙을 추가해줘:
"코드를 변경하면 관련된 문서(README.md, PLAN.md)를 같은 커밋에서 갱신한다.
 방향을 정하는 결정을 내렸으면 DECISIONS.md에 항목을 추가한다."
두 번째 프롬프트가 진짜 핵심입니다 문서화의 실패는 처음 만들 때가 아니라 안 고칠 때 일어납니다. 낡은 문서는 없는 문서보다 나쁩니다 — 틀린 안내를 하니까요. 갱신 규칙을 CLAUDE.md에 박아 두면 이후에는 AI가 알아서 문서를 코드와 함께 고칩니다. 사람은 DECISIONS.md에 쌓이는 기록을 가끔 읽어주기만 하면 됩니다.
스킬(2주차 ⑥)과의 관계 — SKILL.md가 "여러 프로젝트에서 반복하는 절차"의 자리라면, 오늘의 네 파일은 "이 프로젝트의 계획·결정·사용법"의 자리입니다. 절차는 스킬로, 프로젝트의 기억은 문서로.

마무리 체크리스트

  • 임베딩 검색엔진 = 색인 국면(문서 벡터를 미리 DB에) + 검색 국면(①질의 → ②백엔드 → ③질의 임베딩 → ④최근접 탐색 → ⑤목록 반환)
  • 질의 임베딩 모델은 색인 모델과 반드시 동일
  • 키와 호출량 통제를 위해 임베딩 호출은 백엔드에서만
  • 소규모는 모든 문서와 하나하나 비교, 대규모는 전용 벡터 DB — 구조는 동일
  • 출력은 문서 목록: 읽고 판단하는 것은 사람
  • 코드만 남기지 말고 기록을 — PLAN(계획)·DECISIONS(왜)·README(사용·배포)·CLAUDE.md(AI 메모) 네 파일을 코드와 함께 커밋
  • 문서 갱신 규칙을 CLAUDE.md에 박아 두면 이후에는 AI가 코드와 문서를 함께 고친다
다음 강의 — RAG검색엔진이 "문서 목록"을 돌려준다면, RAG는 검색된 문서를 AI가 읽고 "답변"을 씁니다. 목적이 다른 별개 기법을 새로 배웁니다.
