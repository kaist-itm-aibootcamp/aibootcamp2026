WEEK 3 · STEP 2 — 두 가지 검색 패러다임

판결문 검색엔진 —
단어를 찾을 것인가, 의미를 찾을 것인가

2주차에 수집해 둔 판결문 347건으로 검색엔진을 만듭니다. 먼저 키워드 매칭 방식을 직접 써보며 한계를 몸으로 느끼고, 그다음 임베딩 유사도 방식으로 넘어갑니다. 이 페이지의 두 검색창은 모두 실제로 동작합니다.

1

목표 — 판결문 347건 검색엔진

"내 사건과 비슷한 판례를 찾아줘"라는 요구는 모든 리걸테크의 출발점입니다. 우리 재료는 2주차에 구축한 판결문 347건(요약문 + 임베딩)입니다. 같은 재료로 두 방식을 비교합니다.

방식 ① 키워드 매칭

  • 질의어가 문서에 글자 그대로 들어 있는지 확인
  • 구현이 쉽고, 서버 없이 브라우저만으로 동작
  • Ctrl+F의 확장판 — 전통적 검색의 기본

방식 ② 임베딩 유사도

  • 질의와 문서를 같은 좌표계의 벡터로 만들어 거리 비교
  • 단어가 달라도 의미가 같으면 찾아냄
  • 질의를 실시간 임베딩해야 함 → API 호출 필요
2

방식 ① — 키워드 매칭 검색 (직접 써보세요)

판결문 347건의 요약문에서 질의어를 글자 그대로 찾아 많이 등장한 순으로 보여줍니다. 예시 버튼을 눌러보세요.

🔎 키워드 검색기 (요약문 대상 · 브라우저에서만 동작)

욕설 폭언 예견가능성 회사가 알 수 있었다 괴롭힘을 인정하지 않은 사건
질의를 입력하거나 예시 버튼을 눌러보세요.
3

키워드의 한계 — 위에서 겪은 세 가지 실패

1

동의어를 모른다. "폭언"으로는 90건, "욕설"로는 44건이 나오고 두 결과는 서로 다릅니다. 같은 현상을 가리키는 두 단어인데도, 판결문이 어느 단어를 썼는지에 따라 검색이 갈립니다.

2

표현이 다르면 놓친다. "예견가능성"은 법률 용어라 요약문에 5건뿐이지만, "회사가 알 수 있었다"라고 쓰인 판결은 잡지 못합니다 — 뜻은 같아도 글자가 다르기 때문입니다.

3

의도를 모른다. "괴롭힘을 인정하지 않은 사건"을 검색하면 오히려 "괴롭힘"과 "인정"이 많이 등장하는, 괴롭힘을 인정한 사건이 상위에 올라옵니다. 키워드 검색에 부정문·질문의 의도는 전달되지 않습니다.

4

방식 ② — 임베딩 유사도 검색 (직접 써보세요)

모든 판결문은 이미 4,096차원 벡터입니다. 두 벡터의 코사인 유사도를 재면 "의미가 얼마나 비슷한가"가 숫자로 나옵니다. 아래 데모는 판결문 하나를 질의로 삼아 가장 비슷한 판결 5건을 찾습니다 — 미리 계산해 둔 실제 유사도입니다.

🧭 유사 판례 찾기 (실제 코사인 유사도 · 347건 전건 계산)

자연어 질의도 같은 원리 — 실제 스팟체크 기록 질의문 자체를 임베딩하면 문장으로도 검색이 됩니다. 실제 구축 과정의 스팟체크에서 "업무상 적정범위를 넘지 않았다고 보아 괴롭힘을 부정한 사례"라고 질의하자 1·2위가 정확히 그 논리로 기각된 원고패 판결이었고, "사용자의 예견가능성" 질의에는 예견가능성 법리의 대표 사례(카카오톡 증거로 예견가능성 인정, 1,200만 원)가 1위로 나왔습니다. 키워드가 아니라 판시 논리가 검색된 것입니다.
왜 이 데모는 서버 없이 되는가 — 347건끼리의 유사도는 미리 계산해 페이지에 넣어둘 수 있기 때문입니다. 문제는 여러분이 새 질의문을 입력하는 순간 시작됩니다 — 그 문장의 벡터는 미리 계산해 둘 수 없습니다.
5

그런데 — 새 질의를 받으려면 백엔드가 필요하다

사용자가 입력한 질의문을 임베딩하려면 검색할 때마다 OpenRouter API를 호출해야 합니다. 여기서 두 가지 문제가 생깁니다.

💸
문제 1 — 호출마다 비용질의 하나는 몇 원 수준으로 저렴하지만, 공개된 웹앱이라면 누가 몇 번 검색할지 내가 통제할 수 없습니다. 비용의 주체가 "내 크레딧"이라는 게 핵심입니다.
🔑
문제 2 — 키를 감춰야 한다 (치명적)브라우저 자바스크립트에 API 키를 넣으면 누구나 F12(개발자도구) 한 번으로 키를 복사해 내 크레딧으로 무엇이든 호출할 수 있습니다. 정적 웹페이지에는 비밀을 둘 곳이 없습니다.

해법 — 키를 가진 중간 프로그램, 백엔드

브라우저는 백엔드에게만 말하고, 키는 백엔드(내 PC)에만 존재합니다
이것이 이번 주의 핵심 문장 정적 웹앱(1주차)은 "미리 계산된 것"까지만 보여줄 수 있습니다. 사용자 입력을 실시간으로 처리하고, 비밀(키)을 지키려면 백엔드가 필요합니다. 임베딩 검색은 이 원리를 몸으로 배우는 가장 좋은 예제입니다.
6

마무리 체크리스트

  • 키워드 검색은 동의어·표현 차이·의도 앞에서 실패한다 (직접 확인)
  • 임베딩 검색은 단어가 아니라 의미(판시 논리)를 찾는다
  • 문서끼리의 유사도는 사전계산 가능 — 새 질의는 실시간 임베딩이 필요
  • 브라우저 JS에 넣은 API 키는 누구나 볼 수 있다 — 정적 페이지에 비밀은 없다
  • 키를 보관하고 대신 호출하는 중간 프로그램 = 백엔드
다음 강의 두 편 (③·④)③ 임베딩 검색엔진 — KIPRIS 유사 특허 검색과 같은 산업 표준 아키텍처를 이해하고 Claude Code로 직접 구축합니다. ④ RAG — 검색과는 목적이 다른 별개 기법으로, 검색된 문서를 근거로 답변을 생성합니다.
