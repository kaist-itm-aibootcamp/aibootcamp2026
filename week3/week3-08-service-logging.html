WEEK 3 · STEP 8 — 서비스 로그

챗봇에 로그를 달다 —
무엇을 묻고, 뭐라고 답했나

⑤에서 배포한 챗봇은 URL만 알면 누구나 쓸 수 있지만, 지금은 무슨 문답이 오가는지 아무 기록이 남지 않습니다. 이번 실습은 이용자의 질문과 답변을 데이터베이스(Supabase)에 기록하고, 화면 우측 상단의 작은 톱니바퀴(⚙) 뒤에 비밀번호를 아는 관리자만 여는 기록 화면을 답니다.

1

로그의 중요성 — 기능과 운영은 다르다

챗봇이 잘 도는 것과 서비스를 운영하는 것은 다른 일입니다. 운영의 시작이 기록입니다 — 기록이 없으면 서비스가 어떻게 쓰이는지 아무것도 알 수 없습니다.

  • 자산 — 사람들이 무엇을 자주 묻는가, 근거 판례가 빈약했던(=데이터가 약한) 주제는 무엇인가. 다음 개선의 방향이 기록에서 나옵니다
  • 진단 — "어제 이상한 답이 나왔어요"에 답하려면 그때의 질문과 답변이 남아 있어야 합니다. 호출이 몇 번 있었는지로 비용도 검증합니다
  • 책임 — 질문에는 이용자의 관심사, 때로는 민감한 사정이 담깁니다(법률 질문이라면 더욱). 필요한 것만 수집하고, 수집한다는 사실을 알리고, 목적이 끝난 기록은 지웁니다
2

어디에 남기나 — Supabase를 고른 이유

후보는 셋입니다. 서버리스 환경이라는 조건이 선택을 좁혀 줍니다.

후보평가결론
Vercel Logs이미 있지만 며칠 뒤 사라지고, 검색·집계 불가오류 확인용
서버에 파일로서버리스 함수에는 붙박이 디스크가 없습니다 — 함수가 잠들면 쓰던 파일도 사라집니다불가
클라우드 데이터베이스영구 저장, 표로 조회, 어디서나 접속 — 서비스 로그의 표준적인 자리채택
Supabase란무료로 시작할 수 있는 클라우드 데이터베이스 서비스입니다. 가입하면 데이터베이스 하나와 접속 주소(URL)·비밀 키를 받고, 웹 대시보드의 표 화면(Table Editor)에서 저장된 데이터를 직접 열람할 수 있습니다.
무엇을 저장하나표 하나(chat_logs)면 충분합니다 — 시각 · 질문 · 답변 · 비용(원화 환산) · 소요 시간. §1의 원칙대로 필요한 것만 저장하고, 이용자 신원은 수집하지 않습니다.
접속 정보는 어디에⑤의 공식 그대로 — Supabase URL과 키는 Vercel 환경변수에 넣습니다. 코드에는 넣지 않습니다.
3

실습 — 준비 두 가지, 지시 하나

Supabase 계정을 만들어 접속 정보를 Vercel에 넣어 두면, 나머지는 지시 한 번입니다.

어떤 키를 복사하나 — Publishable이 아니라 Secret API Keys를 열면 키가 두 종류 보입니다. Publishable key(sb_publishable_…)는 브라우저에 노출해도 되는 키로, 화면이 DB를 직접 부르는 구조에서 행 단위 보안 규칙(RLS)과 함께 쓰는 것입니다. 우리가 쓸 것은 그 아래 Secret keys — 서버 전용 만능 키라 브라우저에서 쓰면 아예 거부됩니다(sb_secret_…). 우리 구조는 서버리스 함수만 Supabase에 접근하므로 Secret keys의 키를 복사합니다. 이름대로 비밀이니 환경변수로만 다룹니다.
2 표 만들기 — SQL Editor에서 Run 한 번

로그가 쌓일 표(chat_logs)를 한 번 만들어 둡니다. Supabase 왼쪽 메뉴의 SQL Editor → New query에 아래 SQL을 붙여넣고 Run을 누릅니다 — 실제 실행한 장면입니다:

create table if not exists public.chat_logs (
  id           bigint generated always as identity primary key,
  created_at   timestamptz  not null default now(),
  question     text         not null,
  answer       text         not null,
  cost_krw     numeric(12,4),
  duration_sec numeric(8,2)
);
create index if not exists chat_logs_created_at_idx on public.chat_logs (created_at desc);
alter table public.chat_logs enable row level security;

칸 구성은 §2에서 정한 그대로입니다 — 시각·질문·답변·비용·소요 시간(번호와 시각은 자동으로 채워집니다). 실행 결과가 "Success. No rows returned"이면 성공입니다 — 방금 만든 표가 비어 있어 "가져온 행이 없다"는 뜻이지 오류가 아닙니다. 왼쪽 Table Editor에 chat_logs가 보이면 확실합니다.

3 Vercel에 환경변수 추가

Projects 화면에서 프로젝트 카드의 ⋯ → Settings → Environments → Production(⑦ §4에서 간 그 길)으로 들어가 세 개를 추가합니다: SUPABASE_URL(Project URL), SUPABASE_KEY(Secret key), 그리고 관리자 비밀번호의 해시값 ADMIN_PASSWORD_HASH(⑦ §5의 방법으로 새로 만든 값 — 사이트 접속용 PASSWORD_HASH와는 다른 값을 쓰세요). 환경변수는 다음 배포부터 반영됩니다 — 3단계의 push가 그 배포입니다.

4 Claude Code에 지시
💬 프롬프트 — 문답 로그와 관리자 화면 
배포된 판례 챗봇에 문답 로그 기능을 추가한다.

- 이용자가 챗봇에 질문할 때마다 시각, 질문, 답변, 비용(원화 환산),
  소요 시간을 Supabase의 chat_logs 표에 기록해줘.
  접속 정보는 Vercel 환경변수 SUPABASE_URL, SUPABASE_KEY에 있어.
- 화면 우측 상단에 작은 톱니바퀴 아이콘을 추가해줘. 누르면 관리자
  화면이 열리고, 비밀번호를 맞게 넣어야 기록을 볼 수 있어.
- 관리자 비밀번호는 입력값을 해시해서 환경변수 ADMIN_PASSWORD_HASH와
  비교해줘. 비밀번호 원문은 어디에도 저장하지 마.
- 기록 화면은 최근 순서로 시각·질문·답변·비용·소요 시간을 표로 보여줘.
5 push → 재배포 → 기록 확인

변경을 검토하고 commit·push하면 ⑤에서 본 대로 자동 재배포됩니다. 배포된 챗봇에 질문을 두어 개 던진 뒤, Supabase 대시보드의 Table Editor에 행이 쌓이는지 확인하세요.

확인을 꼭 한 번 하세요 — 이 기능은 Supabase가 응답하지 않아도 챗봇이 멈추지 않게, 기록만 조용히 건너뛰도록 만들어져 있습니다. 로그 때문에 본 기능이 죽으면 안 되기 때문인데, 뒤집어 말하면 기록이 안 쌓여도 겉으로는 표가 나지 않는다는 뜻입니다. 설정을 바꾼 뒤에는 질문 → 기록 확인을 한 번 거치고, 잘 안 되면 내주소/api/health를 열어 보세요 — 무엇이 빠졌는지(키 누락, 표 없음, 잘못된 키 종류) 바로 나옵니다.
4

관리자 비밀번호 — ⑦의 해시 방식 그대로

새로 배울 것은 없습니다 — ⑦ §5의 비밀번호 잠금 지름길을 그대로 씁니다.

⑦ §5의 프롬프트로 내 비밀번호의 해시값을 만들고, Vercel 환경변수 ADMIN_PASSWORD_HASH로 추가합니다(실습 3단계). 사이트 접속용 PASSWORD_HASH와는 다른 값을 쓰세요 — 접속 비밀번호는 이용자와 공유하지만 기록은 나만 봐야 하므로, 관문을 둘로 두는 것입니다. 서버는 입력된 비밀번호를 해시해 이 값과 비교할 뿐, 원문은 어디에도 저장되지 않습니다. 원리와 한계는 ⑦ §5에 정리되어 있습니다.

5

기록 보는 화면 — 톱니바퀴 뒤의 관리자 자리

완성되면 이렇게 동작합니다. 일반 이용자에게 보이는 것은 우측 상단의 작은 톱니바퀴(⚙) 하나뿐입니다.

⚙ 클릭우측 상단 → 비밀번호 입력해시를 환경변수와 비교 → 문답 기록 표최근 순 · 시각·질문·답변·비용·시간
  • 비밀번호를 모르면 톱니바퀴를 눌러도 기록에 닿을 수 없습니다 — 이용자 화면과 관리자 화면의 분리
  • 같은 데이터를 Supabase 대시보드의 Table Editor에서도 볼 수 있습니다 — 관리 화면에 문제가 생겨도 데이터는 데이터베이스에 안전하게 남아 있습니다
  • 기록 표 위쪽에는 건수 · 비용 합계 · 질문당 평균 · 평균 소요 시간이 요약되어, 열자마자 서비스 현황이 눈에 들어옵니다
  • 기록이 쌓이면 §1의 자산이 됩니다 — 자주 묻는 주제, 근거가 빈약했던 질문부터 다음 개선을 시작하세요
비용 칸은 추정이 아니라 실제 청구액 — OpenRouter가 응답에 그 요청의 실제 달러 비용을 함께 알려줍니다. 질문 한 번에 API 호출이 최대 세 번(질문 임베딩 + 이어지는 대화의 검색용 재작성 + 답변 생성) 일어나는데, 셋을 더해 원화로 바꿔 저장합니다 — 실측 질문당 1.2~1.5원. 환율은 1달러 = 1,450원 고정이며 환경변수 USD_KRW로 바꿀 수 있습니다.
6

확인 체크리스트

  • 챗봇에 질문하면 시각·질문·답변·비용·소요 시간이 Supabase에 행으로 쌓인다
  • Supabase 접속 정보와 관리자 비밀번호 해시는 Vercel 환경변수에만 있다
  • 우측 상단 톱니바퀴 → 비밀번호 → 최근 순 기록 표가 열린다
  • 로그는 자산이자 책임 — 필요한 것만 수집하고, 목적이 끝나면 지운다
자율 실습 — 내 웹앱에도 로그를자율 실습에서 만든(또는 만들) 내 웹앱에 같은 방식의 로그를 붙여 보세요 — Supabase 프로젝트 하나로 여러 앱의 로그를 받을 수 있습니다.
