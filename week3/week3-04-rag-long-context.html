WEEK 3 · STEP 4 — RAG와 Long Context

RAG — 질문하면 관련 문서를 찾아
읽히고, 근거를 달아 답하게 하기

앞 강의의 검색엔진은 "문서 목록"을 사람에게 돌려줬습니다. RAG는 다른 목적의 기법입니다 — 질문과 관련된 문서를 찾아 AI의 컨텍스트에 로딩하고, 그 문서만 근거로 답변을 쓰게 합니다. 마지막에는 유력한 대안인 Long Context 방식의 현재 수준까지 살펴봅니다.

1

RAG란 무엇인가 — 오픈북 시험을 치르는 AI

LLM에게 그냥 물으면 기억(학습 데이터)으로 답합니다. 기억에는 세 가지 문제가 있습니다 — 학습 이후의 일을 모르고, 내 데이터(사내 문서·수집 판결문)를 모르고, 모르면서 그럴듯하게 지어냅니다(환각).

RAG의 아이디어 한 줄 질문이 들어오면 관련 문서를 검색해서(Retrieval) 질문과 함께 컨텍스트에 로딩하고(Augmented), 그 문서를 근거로 답을 쓰게(Generation) 한다. — 암기 시험을 오픈북 시험으로 바꾸는 것입니다. AI는 "기억나는 대로"가 아니라 "방금 책상에 올려준 자료를 읽고" 답합니다.
🆕
최신·사적 데이터모델이 학습한 적 없는 문서(어제 수집한 판결문, 사내 규정)로도 답할 수 있게 됩니다.
🔗
출처가 달린다어떤 문서를 근거로 답했는지 인용을 강제할 수 있어 검증 가능해집니다.
🚫
환각 억제"제공된 문서로 답할 수 없으면 모른다고 하라"는 지시가 가능해집니다.
검색엔진과의 관계 — 진화가 아니라 분업 — RAG는 앞 강의의 검색엔진을 부품으로 빌려 쓰지만, 두 기법은 목적이 다릅니다. 검색엔진의 사용자는 문서 목록을 직접 읽고 판단하려는 사람이고, RAG의 사용자는 종합된 답을 원하는 사람입니다. 연구자는 대개 둘 다 필요합니다.
2

아키텍처와 데이터 플로우

구조는 앞 강의의 검색엔진에 "챗 모델 호출" 한 단계가 추가된 것입니다. 이번에도 질의 하나의 여행을 따라가 봅니다 — 이번에는 OpenRouter를 두 번(임베딩 모델, 챗 모델) 방문합니다.

데이터 플로우 — "동료들의 따돌림도 손해배상이 되나?" 질문의 몇 초

세로 = 시간 순서 · 화살표 위 = 실제로 오가는 데이터 · ③~⑤는 앞 강의 검색엔진과 동일

앞 강의와 마찬가지로 — 🔑 키는 서버만 갖고, 판결문 347건 원본은 내 PC를 떠나지 않습니다(⑥에서 검색된 5건의 요약만 전송). 소요 시간은 몇 초로 늘어나는데, 대부분 ⑦의 답변 생성입니다.

왜 Chat·Cowork가 아니라 외부 유료 API인가

"답변 생성이라면 Claude Chat이나 Cowork로도 되지 않나?"— 됩니다, 내가 손으로 쓸 때는. 그러나 위 구조도의 ⑥⑦ 자리에는 Chat 화면이 들어갈 수 없습니다.

Chat·Cowork — 사람의 도구

  • 사람이 로그인해 화면에서 직접 실행하는 개인용 서비스
  • 내 연구를 내가 할 때는 이걸로 충분 (Long Context 방식 §5 포함)
  • 그러나 내 프로그램(서버)이 대신 호출할 수 없고, 내 계정 1인분 — 이용자 100명을 받을 수 없음

외부 API — 프로그램의 부품

  • 서버가 자동으로, 동시에, 무인으로 호출하는 인터페이스
  • 쓴 만큼 과금 → 이용자가 늘면 비용도 따라 늘어나는 확장 가능한 구조
  • 그래서 서비스(챗봇·웹앱)를 만들 때는 일반적으로 이 구조를 씁니다
기준 한 줄 — 혼자 쓰는 분석이면 Chat·Cowork로 충분, "다른 사람이 쓰는 서비스"를 만드는 순간 유료 API. 검색엔진 강의에서 임베딩 호출을 API로 한 것과 정확히 같은 이유입니다.
3

컨텍스트에 실제로 담기는 것 — 증강의 실물

⑥단계에서 서버가 실제로 보내는 LLM 호출을 열어보면 이렇게 생겼습니다. 사용자 질문 앞에 검색된 문서 5건이 끼워 넣어진, 하나의 긴 컨텍스트 — 이것이 "증강(Augmented)"의 전부입니다.

4

검색엔진 강의와 같은 방식입니다 — 원하는 것만 서술 → AI가 계획서 → 피드백 → 확정 계획대로 구현. 앞 실습의 검색 서버가 켜져 있는 폴더에서 이어갑니다.

5

대안 — Long Context: 그냥 전부 읽히면 안 되나?

됩니다 — 코퍼스가 충분히 작다면. 최신 LLM의 컨텍스트 창은 수십만~백만 토큰까지 커졌습니다. 두 방식의 차이는 컨텍스트에 무엇을 싣는가로 보면 한눈에 들어옵니다.

6

Long Context 사용 전 점검 — 얼마나 담을 수 있는 모델인가

Long Context 방식을 쓰기로 했다면 첫 질문은 하나입니다 — "내 자료가 이 모델의 컨텍스트 창에 들어가는가?" 컨텍스트 길이는 모델마다 크게 다릅니다.

공개 자료 기준이며 버전에 따라 달라집니다 — 사용 전 그 모델의 공식 문서에서 확인하는 습관이 중요합니다. 참고로 오픈소스 진영에는 1,000만 토큰을 내건 모델(Llama 4 Scout)도 있습니다.

표가 말해주는 것 같은 자료(판결 요지 347건 ≈ 4~5만 토큰)라도 어떤 모델을 고르느냐에 따라 Long Context 방식이 되기도, 안 되기도 합니다. 프런티어 상용 모델과 중국 오픈소스 상위 모델은 100만 토큰 시대에 들어섰고, 국내 모델은 LG K-EXAONE이 26만 토큰으로 수용 가능한 반면 네이버 공개 모델(3.2만)에는 이 자료가 통째로 들어가지 않습니다 — 이 경우 요약본을 쓰거나, 나눠 묻거나, RAG로 전환해야 합니다.

사용 전 점검 3가지

1

내 자료의 토큰 수를 추정한다. 한국어는 대략 글자 수 × 0.7~1이 토큰 수입니다. 판결 요지 347건(약 6.5만 자) ≈ 4~5만 토큰. AI에게 "이 파일 토큰 수 세줘"라고 시켜도 됩니다.

2

모델의 컨텍스트 창과 비교한다. 자료가 창의 절반을 넘으면 여유가 없는 것입니다 — 대화가 오갈수록 컨텍스트는 계속 쌓이기 때문입니다.

3

명목 길이 ≠ 실제 독해력. 창이 크다고 그 끝까지 꼼꼼히 읽는 것은 아닙니다 — 아주 긴 입력에서는 중간의 정보를 놓치는 경향이 보고되어 있으니, 중요한 지시·자료는 앞이나 뒤에 배치하고 여유를 두세요.

7

하이브리드 — 요지는 통째로 싣고, 전문은 골라 읽힌다

RAG와 Long Context는 섞어 쓸 수 있습니다. 아이디어: 컨텍스트에는 판결 요지 347건만 통째로 싣고(목차 역할), 모델이 요지를 훑어 관련 사건을 고르면 그 판결문 전문만 저장된 파일에서 도구로 읽어와 컨텍스트에 추가하는 구조입니다.

하이브리드 구조 — Long Context(요지) + 도구 호출(전문)

임베딩도 벡터 DB도 없이, "요지 훑기"가 검색을 대신합니다

이 구조의 장점

  • 임베딩·벡터 DB·검색 서버가 전혀 필요 없음 — "요지 훑기"가 검색을 대신
  • 답변 근거가 요약이 아니라 판결문 전문 — 판시 이유까지 정밀 인용
  • 사실 Cowork·Claude Code가 일하는 방식이 바로 이것 — 목록을 훑고 필요한 파일만 읽기. 이 부트캠프의 판례 보고서도 이렇게 만들어졌습니다

치르는 비용

  • 요지 4~5만 토큰이 매 질문마다 컨텍스트에 상주 (Long Context의 비용 그대로)
  • 도구 왕복만큼 응답이 느려짐
  • 파일 읽기 도구를 붙일 수 있는 환경이 필요 — Chat 웹화면으로는 안 되고, Cowork·Claude Code 또는 도구 호출을 지원하는 API로 구현

하이브리드로 질문하기 — 프롬프트 예시

💬 Cowork에서 (요지 CSV + 전문 폴더가 연동된 상태) 
연동 폴더에 판결 요지 CSV(347건)와 판결문 전문 파일들(rulings_md/)이 있어.

갈림길은 무엇이었나?

전문 파일을 읽은 다음, 전문을 근거로 사건번호와 판시 대목을
인용해서 답해줘. 요지만 보고 답하지 마.
사실 이렇게 지시하지 않아도 됩니다 (대체로) — Cowork·Claude Code는 과제의 성질에 따라 기본적으로 이렇게 동작합니다: 질문이 코퍼스 전반에 걸치면 목록·요지부터 훑고, 정밀한 근거가 필요해지면 해당 파일을 스스로 열어 읽습니다. 다만 가끔 요지만 보고 요약 수준으로 답하고 마는 경우가 있는데, 답변에 전문 인용이 없다면 그때 위 프롬프트처럼 "고른 사건은 반드시 전문을 읽고 답하라"고 명시적으로 지시하면 됩니다. 지시는 기본 동작을 만드는 것이 아니라 보장하는 장치입니다.
세 구조의 자리 — RAG는 대규모·서비스용, Long Context는 소규모·전체 조망용, 하이브리드는 그 사이 — "요지는 다 보되 전문은 골라 읽어야 하는" 연구 작업에 특히 잘 맞습니다. 코퍼스가 커져 요지조차 컨텍스트에 안 들어가게 되면, 그때 요지 훑기를 임베딩 검색으로 바꾸는 것이 자연스러운 진로입니다. 그리고 이 하이브리드 절차를 매번 프롬프트로 다시 쓰지 않도록 파일(스킬)로 저장하는 방법은 4주차에서 다룹니다.
8

마무리 체크리스트

  • RAG = 검색(기존 검색엔진 재사용) → 증강(질문 앞에 문서 끼워 넣기) → 생성(인용 강제)
  • 답변 생성은 Chat·Cowork가 아니라 외부 API — 서비스는 프로그램이 호출할 수 있어야 확장된다
  • 증강의 실물 = 지시 + 검색 문서 + 질문이 담긴 하나의 컨텍스트
  • 답이 이상하면 생성보다 검색 결과부터 디버깅
  • Long Context는 "통째로 싣기" — 수만 토큰 이내 혼자 쓰는 분석이면 최선의 단순함
  • Long Context 사용 전: 자료 토큰 수 추정 → 모델 컨텍스트 창 확인 (모델마다 3.2만~100만 토큰으로 천차만별)
  • 하이브리드: 요지는 통째로(목차), 전문은 도구로 골라 읽기 — Cowork·Claude Code가 일하는 방식
직접 해보기 — 내 데이터로 구현하기여러분이 스크래핑했거나 보관하고 있는 데이터(리뷰·기사·논문 초록·업무 문서 등)로 셋 중 하나를 구현해 보세요: ① 임베딩 검색엔진 ② RAG 답변 시스템 ③ 하이브리드 질의응답(요지 통째 + 전문 골라 읽기). 판결문은 예시였을 뿐 — 데이터가 바뀌어도 파이프라인과 프롬프트는 동일합니다.
다음 강의 — Vercel 배포: 검색기에서 챗봇까지 (⑤)③의 검색엔진과 오늘 배운 RAG는 아직 내 PC에서만 돕니다. 다음 강의에서 이것을 클라우드(Vercel)에 올려 URL 하나로 누구나 쓰는 서비스로 만듭니다. §7의 하이브리드 절차는 2주차 ⑥에서 배운 방법 그대로 스킬(SKILL.md)로 저장해 두면 좋습니다.
