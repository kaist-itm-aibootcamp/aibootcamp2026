WEEK 3 · STEP 7 — 인증 실습: 문 달기

허용된 사람만 들어오게 —
배포한 챗봇에 이메일 인증으로 문 달기

⑤에서 배포한 판결문 챗봇은 URL만 알면 누구나 들어옵니다. 오늘 그 챗봇에 문을 달아 인증된 사람만 들어오게 만듭니다. 방식은 여러분이 매일 겪는 그것 — 이메일로 6자리 인증코드를 받아 입력하는 흐름입니다. 발송은 별도 유료 서비스 없이 Gmail SMTP + 앱 비밀번호로 합니다.

1

목표 — 배포한 챗봇에 문 달기

오늘 할 일을 실습 언어로 적으면 명확합니다.

지키려는 것
⑤의 챗봇 — 질문할 때마다 내 API 키로 비용이 발생하고, 문답 기록이 쌓이는 서비스
현재 상태
접근 수준 2 — URL을 아는(또는 추측한) 누구나 무제한 질문 가능
목표 상태
접근 수준 3 — 허용 명단의 이메일 주인만 챗봇 사용 가능
오늘 만드는 것
인증(Authentication) — "이 이메일의 주인이 맞는가"를 확인하는 절차
인가는?
가장 단순한 규칙으로 시작 — "인증된 사람은 모두 동일 권한". 역할 구분(인가)은 서비스가 자라면 추가

여기서 용어 둘을 구분해 둡니다 — 인증(authentication)은 "너는 누구인가"를 확인하는 일, 인가(authorization)는 "확인된 너는 무엇을 할 수 있나"를 정하는 일입니다. 오늘의 이메일 인증코드는 앞의 질문에 답하는 장치입니다.

2

설계 — 이메일 인증코드의 전체 흐름

배달앱·은행앱에서 매일 겪는 흐름을 우리 서비스에 그대로 답니다. 등장인물은 셋: 브라우저, 서버리스 함수, 그리고 메일함.

① 이메일 입력브라우저 → ② /api/send-code명단 확인 → 코드 생성
→ Gmail SMTP로 발송 → ③ 메일함6자리 코드 도착 → ④ 코드 입력브라우저 → ⑤ /api/verify-code대조 → 통과 시 세션 발급 → ⑥ 챗봇 입장

서버(어두운 상자)만 아는 것이 세 가지임을 눈여겨보세요:

  • 허용 이메일 명단 — 누구를 들여보낼지는 서버만 압니다. 명단에 없으면 코드 발송 자체를 안 합니다
  • 발송된 코드 — 서버가 잠시(예: 5분) 기억하고 대조 후 폐기합니다
  • Gmail 발송 자격증명 — §3의 앱 비밀번호. 환경변수에 있습니다

이 흐름이 "이메일 주인만 통과"를 보장하는 이유: 코드는 그 메일함으로만 갑니다. 메일함을 열 수 있는 사람 = 그 이메일의 주인이라는 사실을 구글의 로그인 보안에 얹혀 확인하는 셈입니다.

인증을 통과하면 서버가 세션(서명된 쿠키 — "인증됨" 표식)을 발급합니다. 이후 브라우저의 모든 요청에 이 표식이 함께 가고, 챗봇 API는 유효한 세션이 있을 때만 동작합니다. 매 질문마다 인증코드를 다시 받지 않아도 되는 이유입니다.

3

발송 수단 — Gmail SMTP + 앱 비밀번호

서버가 메일을 보내려면 발신 우체국(SMTP 서버)이 필요합니다. 우리는 Gmail의 SMTP 서버를 빌려 씁니다 — 별도 가입도, 비용도, 도메인 설정도 없습니다.

SMTP메일을 발송할 때 쓰는 표준 프로토콜. 코드가 smtp.gmail.com:587에 접속해 "이 주소로 이 내용을 보내라"고 요청합니다.
앱 비밀번호구글 계정 비밀번호 대신 프로그램 전용으로 발급하는 16자리 비밀번호. 계정 본 비밀번호를 코드에 두지 않기 위한 장치이며, 유출 시 그것만 폐기하고 새로 발급하면 됩니다 — 2주차 ④에서 API 키를 다룰 때와 같은 원칙입니다.
발급 방법구글 계정 관리 → 보안 → 2단계 인증을 켠 뒤 → 검색창에 "앱 비밀번호" → 이름 입력 → 생성. 16자리를 복사해 환경변수에 넣습니다.
한도개인 Gmail 기준 일 발송 수백 통 수준 — 인증코드 용도로는 충분하고도 남습니다.
왜 직접 메일 서버를 세우지 않나 SMTP 서버 자체는 누구나 세울 수 있습니다. 문제는 평판입니다. 수신 측(Gmail·네이버)은 낯선 발신 서버의 메일을 스팸으로 분류하거나 거부합니다. SPF·DKIM 같은 인증 설정을 다 갖춰도 신규 서버는 평판이 없어 배달이 불안정합니다. Gmail을 빌리면 구글의 평판으로 발송되므로 이 문제가 사라집니다. 규모가 커지면 전문 발송 서비스로 옮깁니다(§5).
4

구현 프롬프트 (강사 데모 · 자율 실습)

수업에서는 강사가 ⑤의 챗봇에 이 인증을 붙여 실제 메일이 도착하는 것까지 시연합니다. 각자 구현은 자율 과제 — 아래 프롬프트를 ⑤의 챗봇 프로젝트 폴더에서 실행하면 됩니다.

💬 완성 프롬프트 — 이메일 인증 추가 
이 판결문 챗봇 웹앱에 이메일 인증코드 로그인을 추가해줘.
Vercel에 배포되어 있는 프로젝트야.

흐름:
1. 첫 화면은 이메일 입력 폼. 인증 전에는 챗봇 화면도, 검색·챗봇 API도
   절대 동작하면 안 돼.
2. /api/send-code : 입력된 이메일이 허용 명단(환경변수 ALLOWED_EMAILS,
   쉼표 구분)에 있으면 6자리 코드를 생성해 Gmail SMTP로 발송.
   명단에 없으면 "발송되지 않았습니다"라고만 답하고 이유는 알려주지 마.
3. 코드는 서버 측에 5분간만 유효하게 보관하고, 검증 3회 실패 시 폐기해줘.
4. /api/verify-code : 코드가 맞으면 세션(서명된 쿠키)을 발급.
   이후 /api/chat과 /api/search는 유효한 세션이 있을 때만 동작하게 해줘.
5. SMTP 설정은 환경변수로: SMTP_USER(내 지메일 주소), SMTP_APP_PASSWORD(앱
   비밀번호). smtp.gmail.com 587 포트 사용. 자격증명을 코드에 넣지 마.
6. 메일 제목은 "[판결문 챗봇] 인증코드 안내", 본문에 코드와 유효시간을 담아줘.

이 값들의 "파일" 버전 — .env

내 PC에서 개발하고 시험할 때는 이런 값들을 보통 프로젝트 폴더의 .env라는 파일에 이름=값 한 줄씩 저장합니다. 코드는 "이 이름의 환경변수를 읽어라"라고만 되어 있어서, 내 PC에서는 .env 파일에서, Vercel에서는 위 설정 화면에서 같은 이름을 찾아 읽습니다. ⑤의 New Project 화면에 있던 Import .env 버튼이 바로 이 파일을 통째로 올려주는 기능입니다.

📄 .env 파일 샘플 — 값은 각자의 것으로 
SMTP_USER=mybootcamp@gmail.com
SMTP_APP_PASSWORD=abcd efgh ijkl mnop
ALLOWED_EMAILS=kim@itm.kaist.ac.kr,park@itm.kaist.ac.kr,lee@itm.kaist.ac.kr
OPENROUTER_API_KEY=sk-or-v1-...(비밀키)
.env는 비밀 모음입니다 키·비밀번호·명단이 평문으로 들어 있으므로 절대 GitHub에 올라가면 안 됩니다 — .gitignore에 .env가 들어 있는지 확인하세요. Claude Code에 ".env가 커밋되지 않게 확인해줘"라고 한 번 시키면 됩니다.

프롬프트의 2번 마지막 문장(이유를 알려주지 않기)과 3번(시간 제한·시도 제한)은 사소해 보이지만 실제 보안 관행입니다 — 공격자에게 명단 탐색과 무차별 대입의 실마리를 주지 않는 장치입니다. 1번의 "API도 동작하면 안 돼"도 중요합니다: 화면만 가리고 API를 열어 두면, 화면을 우회해 직접 API를 부르는 사람에게는 문이 없는 것과 같습니다.

5

지름길 — 나만 쓴다면: 비밀번호 하나로 잠그기

§2~§4의 이메일 인증은 여러 사람을 명단으로 들이는 문입니다. 그런데 배포는 하고 싶고 쓰는 사람은 나 하나라면? 문서 파일에 비밀번호를 걸듯, 사이트 전체에 비밀번호 하나를 거는 훨씬 간단한 방법이 있습니다. SMTP도, 명단도, 메일 발송도 필요 없습니다.

원리 — 비밀번호가 아니라 "비밀번호의 지문"을 저장한다

가장 쉬운 생각은 비밀번호를 코드에 그대로 적는 것(하드코딩)이지만, 코드는 GitHub에 올라가는 순간 공개됩니다. 그래서 한 단계만 더 갑니다 — 단방향 암호화(해시)입니다. 비밀번호를 해시 함수(예: SHA-256)에 넣으면 고정 길이의 문자열이 나오는데, 이 값에서 원래 비밀번호로 되돌리는 것은 불가능합니다. 지문에서 사람을 복원할 수 없는 것과 같습니다.

1
내 비밀번호의 해시값 만들기
💬 Claude Code 프롬프트 
비밀번호 문자열을 SHA-256으로 해시해 16진수 문자열로 출력하는
아주 짧은 파이썬 스크립트를 만들어 실행해줘.
비밀번호는 실행할 때 내가 직접 입력할게 (코드나 대화에 남기지 않게).

내가 정한 비밀번호를 넣으면 a3f8c2… 같은 64자 해시값이 나옵니다. 이 값은 비밀번호가 아니므로 다뤄도 부담이 덜합니다.

2
해시값을 Vercel 환경변수에 저장

Vercel 프로젝트 설정 → Environment Variables에 PASSWORD_HASH라는 이름으로 방금 나온 해시값을 넣습니다. ⑤에서 OpenRouter 키를 넣던 바로 그 자리입니다.

3
사이트에 비밀번호 입구 달기
💬 Claude Code 프롬프트 
배포한 사이트에 비밀번호 입구를 달아줘.
1. 첫 화면에서 비밀번호 하나만 입력받는다.
2. 서버(/api/login)는 입력값을 SHA-256으로 해시해 환경변수
   PASSWORD_HASH와 비교하고, 일치하면 세션을 발급한다.
3. 세션이 없으면 화면과 모든 API가 동작하지 않아야 한다.
4. 틀렸을 때는 "비밀번호가 올바르지 않습니다"만 안내한다.
5. 원문 비밀번호는 어디에도 저장하거나 기록(log)하지 않는다.

재배포하면 끝 — 내가 정한 비밀번호를 아는 사람만 들어올 수 있습니다.

환경변수에서 한 단계 더 ⑤에서 "비밀은 서버의 환경변수에"를 배웠습니다. 이 방식은 거기서 한 걸음 더 나갑니다 — 환경변수에조차 원문이 아니라 해시만 둡니다. 환경변수가 통째로 노출되는 사고가 나도 비밀번호 원문은 복원되지 않습니다. 같은 원리가 실제 서비스의 회원 비밀번호 저장에도 쓰입니다(그쪽은 솔트 등 장치가 더 붙습니다).
지름길의 한계 — 이것은 "잠금"이지 "인증"이 아닙니다 비밀번호 하나로는 누가 들어왔는지 구분할 수 없습니다. 식별 없이 문만 있는 셈이라, 비밀번호가 한 번 공유되면 통제가 끝나고, 접근 기록도 사람별로 남지 않습니다. 무차별 대입을 견디도록 비밀번호는 길게(문장형 권장) 정하세요. 나 혼자 또는 신뢰하는 소수와 쓰는 사이트라면 이 정도로 충분하고, 여러 사람을 명단으로 관리하고 기록이 필요해지면 그때 §2~§4의 이메일 인증으로 올라가면 됩니다.
6

실무에서는 — 직접 만들지 않는 선택지
