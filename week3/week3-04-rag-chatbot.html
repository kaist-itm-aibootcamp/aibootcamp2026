WEEK 3 · STEP 4 — RAG: 판례 챗봇

RAG — 질문하면 관련 문서를 찾아
읽히고, 근거를 달아 답하게 하기

앞 강의의 검색엔진은 "문서 목록"을 사람에게 돌려줬습니다. RAG는 다른 목적의 기법입니다 — 질문과 관련된 문서를 찾아 AI의 컨텍스트에 로딩하고, 그 문서만 근거로 답변을 쓰게 합니다. 유력한 대안인 Long Context 방식과의 비교는 ⑥ 강의에서 따로 다룹니다.

1

RAG란 무엇인가 — 오픈북 시험을 치르는 AI

LLM에게 그냥 물으면 기억(학습 데이터)으로 답합니다. 기억에는 세 가지 문제가 있습니다 — 학습 이후의 일을 모르고, 내 데이터(사내 문서·수집 판결문)를 모르고, 모르면서 그럴듯하게 지어냅니다(환각).

RAG의 아이디어 한 줄 질문이 들어오면 관련 문서를 검색해서(Retrieval) 질문과 함께 컨텍스트에 로딩하고(Augmented), 그 문서를 근거로 답을 쓰게(Generation) 한다. — 암기 시험을 오픈북 시험으로 바꾸는 것입니다. AI는 "기억나는 대로"가 아니라 "방금 책상에 올려준 자료를 읽고" 답합니다.
🆕
최신·사적 데이터모델이 학습한 적 없는 문서(어제 수집한 판결문, 사내 규정)로도 답할 수 있게 됩니다.
🔗
출처가 달린다어떤 문서를 근거로 답했는지 인용을 강제할 수 있어 검증 가능해집니다.
🚫
환각 억제"제공된 문서로 답할 수 없으면 모른다고 하라"는 지시가 가능해집니다.
검색엔진과의 관계 — 진화가 아니라 분업 — RAG는 앞 강의의 검색엔진을 부품으로 빌려 쓰지만, 두 기법은 목적이 다릅니다. 검색엔진의 사용자는 문서 목록을 직접 읽고 판단하려는 사람이고, RAG의 사용자는 종합된 답을 원하는 사람입니다. 연구자는 대개 둘 다 필요합니다.
2

아키텍처와 데이터 플로우

구조는 앞 강의의 검색엔진에 "챗 모델 호출" 한 단계가 추가된 것입니다. 이번에도 질의 하나의 여행을 따라가 봅니다 — 이번에는 OpenRouter를 두 번(임베딩 모델, 챗 모델) 방문합니다.

데이터 플로우 — "동료들의 따돌림도 손해배상이 되나?" 질문의 몇 초

세로 = 시간 순서 · 화살표 위 = 실제로 오가는 데이터 · ③~⑤는 앞 강의 검색엔진과 동일

앞 강의와 마찬가지로 — 🔑 키는 서버만 갖고, 판결문 347건 원본은 내 PC를 떠나지 않습니다(⑥에서 검색된 20건의 요약만 전송). 소요 시간은 십수 초로 늘어나는데, 대부분 ⑦의 답변 생성입니다 (실측: 임베딩 1초 + 생성 12초 — §5의 실제 기록 참조).

왜 Chat·Cowork가 아니라 외부 유료 API인가

"답변 생성이라면 Claude Chat이나 Cowork로도 되지 않나?"— 됩니다, 내가 손으로 쓸 때는. 그러나 위 구조도의 ⑥⑦ 자리에는 Chat 화면이 들어갈 수 없습니다.

Chat·Cowork — 사람의 도구

  • 사람이 로그인해 화면에서 직접 실행하는 개인용 서비스
  • 내 연구를 내가 할 때는 이걸로 충분 (⑥의 Long Context 방식 포함)
  • 그러나 내 프로그램(서버)이 대신 호출할 수 없고, 내 계정 1인분 — 이용자 100명을 받을 수 없음

외부 API — 프로그램의 부품

  • 서버가 자동으로, 동시에, 무인으로 호출하는 인터페이스
  • 쓴 만큼 과금 → 이용자가 늘면 비용도 따라 늘어나는 확장 가능한 구조
  • 그래서 서비스(챗봇·웹앱)를 만들 때는 일반적으로 이 구조를 씁니다
기준 한 줄 — 혼자 쓰는 분석이면 Chat·Cowork로 충분, "다른 사람이 쓰는 서비스"를 만드는 순간 유료 API. 검색엔진 강의에서 임베딩 호출을 API로 한 것과 정확히 같은 이유입니다.
3

컨텍스트에 실제로 담기는 것 — 증강의 실물

⑥단계에서 서버가 보내는 LLM 호출을 열어보면 이렇게 생겼습니다 (구조가 보이게 줄인 축약본 — 한 질문의 전체 실물 기록은 §5에 있습니다). 사용자 질문 앞에 검색된 판례 요약 20건이 끼워 넣어진, 하나의 긴 컨텍스트 — 이것이 "증강(Augmented)"의 전부입니다.

POST https://openrouter.ai/api/v1/chat/completions

노란 글씨 = 개발자가 고정한 지시, 파란 글씨 = 방금 검색된 판례 요약 20건, 초록 글씨 = 사용자 질문. 이 전체(약 3천 토큰)가 한 번의 호출에 담긴 하나의 컨텍스트이고, 모델은 "이 자료를 읽고 마지막 질문에 답하라"는 오픈북 문제지를 받은 셈입니다. 검색이 문서를 잘못 고르면 문제지 자체가 엉뚱해집니다 — RAG 품질의 절반은 검색 품질입니다.

4

실습 — 판례 챗봇, 계획부터 대화로

검색엔진 강의와 같은 방식입니다 — 원하는 것만 서술 → AI가 계획서 → 피드백 → 확정 계획대로 구현. 앞 실습의 검색 서버가 켜져 있는 폴더에서 이어갑니다.

1
원하는 것만 서술한다
💬 1단계 — 요구 서술 
나는 개발자가 아니야. 바로 코드를 짜지 말고 계획서부터 만들어줘.

내가 원하는 것:
- 지금 만든 판례 검색 서비스에 챗봇 기능을 추가하고 싶어
- 질문을 하면, 판결문 347건에서 관련 판례를 찾아 그것을
  근거로 답해주는 방식(RAG)이면 좋겠어
- 답변에는 어떤 판결을 근거로 했는지 표시되어야 해
- 근거가 없으면 아는 척하지 말고 모른다고 해야 해

계획서에 무엇을 만들지, 순서, 내가 확인할 지점을 넣고,
결정이 필요한 것은 나에게 질문해줘.
2
AI가 계획서 초안과 질문 4가지를 돌려준다 — 실제 돌아온 질문
📋 계획서 v1 (요약) — 기존 서버에 질문 응답 기능 추가 + 챗봇 화면. 흐름: 질문 → 기존 검색 재사용 → 찾은 판례를 근거로 챗 모델이 답변 생성. 이어서 결정이 필요한 질문 네 개가 왔고, 각 질문에는 선택지와 AI의 추천안이 붙어 있었습니다:

(a) 챗봇이 답변할 때 무엇을 근거로 읽게 할까요? 답변의 깊이와 비용을 가장 크게 좌우하는 선택입니다.
(b) 답변을 만드는 AI 모델은 어느 쪽으로 할까요? 네 가지 모두 연결 테스트를 통과했습니다.
(c) 대화를 이어가는 방식은 어떻게 할까요?
(d) 챗봇을 화면 어디에 둘까요? 지금은 왼쪽에 검색·결과, 오른쪽에 판결문 전문이 들어가 있습니다.
3
질문에 답한다 — 실제 답한 그대로
(a) 근거 → 요약만 20건
(b) 모델 → "네가 가성비 좋은 걸로 추천해서 계획서에 이유와 함께 적어줘. 딥시크 등 OpenRouter에서 널리 활용되는 추론 모델 고려"
(c) 대화 방식 → 이어지는 대화 (AI 추천안 수락)
(d) 화면 위치 → 상단 탭으로 전환 (AI 추천안 수락)

결정 네 개의 답이 세 갈래입니다 — 둘은 추천안 그대로 수락하고, (a)는 비용을 아끼면서 근거 폭을 넓히는 쪽(전문 몇 건 대신 요약 20건)을 직접 골랐고, (b)는 판단 자체를 AI에게 위임하되 "추천 이유를 계획서에 적어라"고 요구했습니다. 모르는 결정은 이렇게 되넘기면 됩니다 — 근거가 문서로 남아 나중에 검토할 수 있습니다.

4
AI가 실측으로 답하고 계획을 확정한다 — 실제 돌아온 답변

만들 것 — 상단에 [검색] [챗봇] 탭이 생기고, 챗봇에 질문하면 판결 347건 중 가까운 20건을 찾아 그 요약을 근거로 답합니다. 답변에는 [1] [7] 같은 근거 번호가 붙고, 답변 아래 근거 판결이 카드로 나오며 클릭하면 오른쪽 패널에 전문이 열립니다. 근거가 없으면 "제가 가진 347건의 판결문으로는 답변드릴 수 없습니다"라고 답합니다.

모델 선택을 맡기셔서 실제로 시험해 봤습니다. 후보 6개에 진짜 챗봇과 똑같은 프롬프트를 넣고, 판례에 답이 있는 질문과 무관한 질문("이혼 재산분할 비율") 두 가지를 던졌습니다. 결과가 뚜렷했습니다. GLM 4.7 Flash는 두 질문 모두 빈 응답을 내놔 탈락했고, 나머지 다섯은 모두 무관한 질문을 정확히 거절했습니다. 요청하신 "아는 척하지 않기"는 다섯 모두 통과한 셈입니다.

DeepSeek V4 Flash를 추천드립니다. 질문당 약 2원인데, Claude(약 40원)와 함께 유일하게 "회사가 징계·전보를 다한 경우에는 책임이 부정되기도 한다"는 반대 사례를 스스로 짚었습니다. 법률 자료에서 예외를 함께 말해주는 건 중요한 차이라고 봤습니다. 20배 싼 값에 그 수준을 낸 게 결정적이었습니다. 단점은 응답이 16초로 느린 것이라, 답변을 한 글자씩 흘려보내는 스트리밍 출력을 함께 만들어 체감 대기를 줄이겠습니다. 그래도 답답하면 모델 이름 한 줄만 바꾸면 됩니다.

미리 아셔야 할 한계가 하나 있습니다. 요약만 근거로 쓰기로 하셨는데, 요약은 한 건에 190자라 법원이 왜 그렇게 판단했는지는 담겨 있지 않습니다. "왜 그렇게 판단했나요?"류 질문에는 답이 얕아집니다. 확인 지점 1에서 실제 답변을 보시고 아쉬우면 상위 3~5건의 전문을 추가하는 쪽으로 바꿀 수 있습니다(질문당 2원 → 10원). 그리고 챗봇은 매번 20건만 보므로 "347건 중 승소율은?" 같은 전체 통계 질문은 답하지 못합니다. 그건 검색 탭의 요약 차트가 담당합니다.

위임한 결정 하나에 후보 6개 실측 → 추천과 이유 → 비용 숫자 → 단점과 보완책이 돌아왔습니다 — 3단계의 "추천해서 이유와 함께 적어줘" 한 줄이 만든 결과입니다. 묻지 않은 한계(요약 근거의 얕음, 전체 통계 불가)를 먼저 고지하고 나중에 바꿀 경로까지 열어둔 것도 눈여겨보세요 — 사람 전문가에게 기대하는 바로 그 보고 형태입니다.

5
확정된 계획서대로 구현시킨다
💬 4단계 — 구현 지시 
계획서 v2대로 구현해줘. 계획에 없는 것은 먼저 물어봐.
완성되면 "동료 직원들의 따돌림만으로도 손해배상을 받을 수 있어?"로
시험 질문을 해서 답변과 근거를 보여줘.

구현 완료 보고 — 실제 돌아온 그대로

판례에 답이 있는 질문("회사에도 책임을 물을 수 있나요")에는 회사 책임이 인정된 경우와 부정된 경우를 갈래로 나눠 답했습니다. 계획서에서 이 모델을 고른 결정적 이유였던 "반대 사례를 함께 짚는" 동작이 실제로 나왔습니다. 범위 밖 질문("이혼 재산분할")에는 정확히 거절했고, 이때는 근거 카드도 표시되지 않습니다. 애매한 질문("녹음 파일이 몇 개나 필요한가요")에는 "구체적인 숫자 기준은 답할 수 없다"고 먼저 밝힌 뒤 판례에서 읽히는 경향만 설명했습니다. 금액을 지어낼 위험이 있는 질문에도 판례에 있는 금액만 인용했습니다.

구현 중 버그 두 개를 잡았습니다. 하나는 스트리밍 응답의 한글이 전부 깨지는 문제였습니다. OpenRouter의 스트리밍 응답에는 문자 인코딩 정보가 없어서 라이브러리가 서유럽 문자로 잘못 읽고 있었습니다. 다른 하나는 모델이 [6, 13, 17]처럼 한 괄호에 여러 번호를 묶어 쓰는데 제 코드가 [6] 형태만 인식해서, 근거 카드가 실제보다 적게 나오던 문제입니다. 둘 다 고쳤고 재검증했습니다.

실제 동작 확인 — 답변은 2~4초 만에 첫 글자가 나오기 시작해 20~30초에 완성됩니다. "회사에도 책임을 물을 수 있나요" 질문에는 근거 카드 13건과 본문 인용 칩 25개가 붙었고, 칩이든 카드든 클릭하면 오른쪽 패널에 그 판결문 전문이 열립니다. 이어지는 대화도 작동합니다. "그중에 회사 책임이 부정된 사례만 알려줘"라고 하면 내부적으로 "회사 책임이 부정된 직장 내 괴롭힘으로 인한 우울증 판례"로 다시 써서 검색합니다. 이 다시 쓴 문장은 답변 위에 작게 표시되니 챗봇이 무엇을 찾았는지 확인하실 수 있습니다.

한 가지 눈여겨보실 점이 있습니다. 위자료 금액을 묻는 질문에서 챗봇은 요약문에 적힌 위자료 금액을 인용하는데, 근거 카드에 표시되는 금액은 주문에서 뽑은 전체 인용액(치료비·일실수입 포함)입니다. 그래서 같은 판결인데 본문의 금액과 카드의 금액이 다르게 보일 수 있습니다. 둘 다 맞는 값이지만 성격이 다른 숫자입니다.

계획서에 적었던 대로 요약만 근거로 쓰는 한계도 그대로 남아 있습니다. "법원이 왜 그렇게 판단했는지"를 깊이 파고들면 답이 얕아집니다. 몇 가지 질문을 직접 해보시고 아쉬우면 상위 3~5건의 전문을 근거에 추가하는 쪽으로 바꿀 수 있습니다(질문당 3원 → 10원 정도).

확인 지점을 계획서에 박아 둔 덕에, 완료 보고가 "됩니다" 한 줄이 아니라 검증 시나리오 4종(답 있는·범위 밖·애매한·금액 질문) → 고친 버그 → 실측 성능 → 숫자 해석 주의 → 남은 한계의 순서로 돌아왔습니다.

직장 내 괴롭힘으로 우울증이 생겼을 때 회사에도 책임을 물을 수 있나요?

네, 직장 내 괴롭힘으로 인한 우울증 발생 시 회사(사용자)에게도 책임을 물을 수 있는 경우가 있습니다. 다만, 모든 경우에 인정되는 것은 아니며, 구체적인 상황과 회사의 대응에 따라 법원의 판단이 갈립니다.

판결문을 근거로 정리하면 다음과 같습니다.

1. 회사의 책임이 인정된 사례 (사용자책임 또는 보호의무 위반)

회사가 가해자를 적절히 관리·감독하지 않았거나, 괴롭힘 발생 시 필요한 예방 또는 시정 조치를 하지 않은 경우 책임을 집니다.

  • 직접적 가해 행위에 대한 사용자책임: 상사(팀장, 이사 등)의 괴롭힘 행위가 업무 수행과 관련되어 있다고 보아 회사가 책임을 진 경우 1.
  • 보호의무 위반: 괴롭힘 발생 후 회사가 피해 근로자와 가해자를 분리하는 등 적절한 보호조치를 취하지 않은 경우 10. 또는 괴롭힘을 알고도 방치한 경우 7.
  • 공동불법행위 책임: 회사의 운영진(상무, 이사 등)이 직접 가해 행위에 가담하거나 공동으로 괴롭힘을 한 경우 2.
2. 회사의 책임이 부정된 사례

다음과 같은 경우에는 회사에 대한 청구가 기각되기도 합니다.

  • 가해 행위가 업무와 무관하다고 판단된 경우: 가해자가 동료이고, 그 행위가 회사의 업무 수행과 관련이 없다고 보는 경우 11 (단, 이 사건은 가해 개인에 대한 책임은 인정됨).
  • 회사가 적절한 조치를 취한 경우: 괴롭힘 신고 후 회사가 내부 조사를 실시하고, 가해자에게 징계 또는 전보 등의 조치를 취했다고 인정되는 경우 12.
  • 괴롭힘 사실 자체가 증명되지 않은 경우: 원고가 주장하는 괴롭힘 행위가 증거 부족으로 인정되지 않아, 회사의 책임 논의 자체가 이루어지지 않은 경우 3, 8, 15, 18.

실제 화면입니다 — 이 답변 아래로 근거 판결 카드 13건이 이어지고, 본문의 번호 칩이든 카드든 클릭하면 오른쪽 패널에 해당 판결문 전문이 열립니다. 인정 갈래와 부정 갈래를 나눠 답한 것, 즉 계획서에서 이 모델을 고른 결정적 이유였던 동작이 첫 질문에서 그대로 나왔습니다.

RAG의 실패 모드도 알아두기 RAG의 품질은 ①검색이 좋은 문서를 찾았는가에 달려 있습니다. 답이 이상하면 생성보다 먼저 검색 결과부터 확인하는 것이 디버깅 순서입니다.

{ "model": "deepseek/deepseek-v4-flash", "max_tokens": 3000, "temperature": 0.2, "stream": true }

stream: true는 답변을 다 쓴 뒤 한 번에 주지 말고 쓰는 대로 조금씩 보내달라는 뜻이고(§4 완성 보고의 스트리밍 출력이 이것입니다), temperature: 0.2는 답변을 되도록 일관되게 하라는 뜻입니다(0에 가까울수록 매번 비슷해집니다).

system 메시지 — AI에게 주는 규칙 (671자, 보낸 그대로)

너는 한국의 '직장 내 괴롭힘' 관련 민사판결 347건만을 근거로 답하는 조수다. 사용자는 법률 전문가가 아니다. 반드시 지킬 규칙: 1. 아래 <판례>에 적힌 내용만 근거로 삼는다. 네가 따로 아는 법률지식이나 일반론으로 보충하지 마라. <판례>에 없는 법조문·판례번호·금액을 지어내지 마라. 2. 답변의 각 주장 끝에 근거가 된 판례의 번호를 [1], [7]처럼 붙인다. 반드시 <판례>에 실제로 있는 번호만 쓴다. 3. <판례>만으로 질문에 답할 수 없으면, 추측하지 말고 정확히 이렇게 답한다: "제가 가진 347건의 판결문으로는 답변드릴 수 없습니다" 그리고 왜 그런지 한 줄로 설명한다. 일부만 답할 수 있으면 답할 수 있는 부분만 답하고, 나머지는 근거가 없다고 밝힌다. 4. 결론이 갈리는 쟁점이면 **반대 방향의 사례도 함께** 제시한다. (예: 회사 책임이 인정된 사례와 부정된 사례) 5. 한국어로, 법률용어는 풀어서 설명한다. 길게 늘어놓지 말고 핵심부터 말한다. 사례를 그냥 나열하지 말고, 갈래를 잡아 정리한다. 답변에 "<판례>"라는 표시를 그대로 쓰지 마라. 필요하면 "판결문"이라고 쓴다. 6. 너는 변호사가 아니며 이 답변은 법률 자문이 아니다. 다만 매 답변마다 그 사실을 반복해 적지는 마라 (화면에 이미 표시된다).

AI는 판결문 347건을 갖고 있지 않습니다. 매번 질문에 맞는 20건을 골라 그때그때 메시지에 담아 보내고, AI는 그 20건만 보고 답합니다.

2

보내는 메시지의 대부분이 근거 자료입니다. 질문은 40자인데 근거는 5,252자입니다.

3

규칙(system)과 자료(user)를 나눠서 보냅니다. 규칙은 매번 같고, 자료는 매번 다릅니다.

4

"근거가 없으면 모른다고 하라"를 규칙에 적어둡니다. 이 문장이 없으면 AI는 자기가 아는 일반 법률지식으로 그럴듯하게 지어냅니다.

5

인용 번호는 검증합니다. AI가 붙인 번호를 그대로 믿지 않고, 실제 목록에 있는 번호인지 프로그램이 확인합니다.

  • RAG = 검색(기존 검색엔진 재사용) → 증강(질문 앞에 문서 끼워 넣기) → 생성(인용 강제)

  • 증강의 실물 = 지시 + 검색 문서 + 질문이 담긴 하나의 컨텍스트
  • 답이 이상하면 생성보다 검색 결과부터 디버깅
  • 질문 한 번 = API 두 번(임베딩 + 챗) · 비용 약 1원대 — 어느 서버에서 돌릴지는 OpenRouter가 골라 분산
