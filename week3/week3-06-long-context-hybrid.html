RAG vs Long Context —
검색 없이 통째로 읽히면 안 되나?

④의 RAG는 검색으로 고른 문서만 컨텍스트에 실었습니다. 이 강의는 다른 갈래의 쟁점입니다 — 컨텍스트 창이 수십만~백만 토큰으로 커진 지금, 자료를 통째로 실어 버리는 Long Context 방식이 언제 성립하는지 점검하고, 요지는 통째로·전문은 골라 읽는 하이브리드까지 세 구조의 자리를 정리합니다.

1

Long Context — 그냥 전부 읽히면 안 되나?

됩니다 — 코퍼스가 충분히 작다면. ④에서 만든 챗봇과의 차이는 컨텍스트에 무엇을 싣는가로 보면 한눈에 들어옵니다.

Long Context 방식의 매력 검색 단계가 없으므로 백엔드도, 임베딩도 필요 없습니다. 판결 요지 CSV를 Chat·Cowork에 첨부하고 "전부 읽고 답해줘"라고 하면 끝 — 실제로 이 부트캠프의 판례 분석 보고서(895건 유형 분류)도 이 계열의 방식으로 만들어졌습니다. 혼자 쓰는 연구라면 가장 단순하고 강력한 선택지입니다. (서비스로 만들 때는 ④에서 본 이유 — 프로그램이 호출할 수 있어야 한다 — 로 다시 API·비용 문제가 돌아옵니다.)

2

Long Context 사용 전 점검 — 얼마나 담을 수 있는 모델인가

Long Context 방식을 쓰기로 했다면 첫 질문은 하나입니다 — "내 자료가 이 모델의 컨텍스트 창에 들어가는가?" 컨텍스트 길이는 모델마다 크게 다릅니다.

공개 자료 기준이며 버전에 따라 달라집니다 — 사용 전 그 모델의 공식 문서에서 확인하는 습관이 중요합니다. 참고로 오픈소스 진영에는 1,000만 토큰을 내건 모델(Llama 4 Scout)도 있습니다.

표가 말해주는 것 같은 자료(판결 요지 347건 ≈ 4~5만 토큰)라도 어떤 모델을 고르느냐에 따라 Long Context 방식이 되기도, 안 되기도 합니다. 프런티어 상용 모델과 중국 오픈소스 상위 모델은 100만 토큰 시대에 들어섰고, 국내 모델은 LG K-EXAONE이 26만 토큰으로 수용 가능한 반면 네이버 공개 모델(3.2만)에는 이 자료가 통째로 들어가지 않습니다 — 이 경우 요약본을 쓰거나, 나눠 묻거나, RAG로 전환해야 합니다.

사용 전 점검 3가지

1

내 자료의 토큰 수를 추정한다. 한국어는 대략 글자 수 × 0.7~1이 토큰 수입니다. 판결 요지 347건(약 6.5만 자) ≈ 4~5만 토큰. AI에게 "이 파일 토큰 수 세줘"라고 시켜도 됩니다.

2

모델의 컨텍스트 창과 비교한다. 자료가 창의 절반을 넘으면 여유가 없는 것입니다 — 대화가 오갈수록 컨텍스트는 계속 쌓이기 때문입니다.

3

명목 길이 ≠ 실제 독해력. 창이 크다고 그 끝까지 꼼꼼히 읽는 것은 아닙니다 — 아주 긴 입력에서는 중간의 정보를 놓치는 경향이 보고되어 있으니, 중요한 지시·자료는 앞이나 뒤에 배치하고 여유를 두세요.

3

하이브리드 — 요지는 통째로 싣고, 전문은 골라 읽힌다

RAG와 Long Context는 섞어 쓸 수 있습니다. 아이디어: 컨텍스트에는 판결 요지 347건만 통째로 싣고(목차 역할), 모델이 요지를 훑어 관련 사건을 고르면 그 판결문 전문만 저장된 파일에서 도구로 읽어와 컨텍스트에 추가하는 구조입니다.

하이브리드 구조 — Long Context(요지) + 도구 호출(전문)

임베딩도 벡터 DB도 없이, "요지 훑기"가 검색을 대신합니다

이 구조의 장점

  • 임베딩·벡터 DB·검색 서버가 전혀 필요 없음 — "요지 훑기"가 검색을 대신
  • 답변 근거가 요약이 아니라 판결문 전문 — 판시 이유까지 정밀 인용
  • 사실 Cowork·Claude Code가 일하는 방식이 바로 이것 — 목록을 훑고 필요한 파일만 읽기. 이 부트캠프의 판례 보고서도 이렇게 만들어졌습니다

치르는 비용

  • 요지 4~5만 토큰이 매 질문마다 컨텍스트에 상주 (Long Context의 비용 그대로)
  • 도구 왕복만큼 응답이 느려짐
  • 파일 읽기 도구를 붙일 수 있는 환경이 필요 — Chat 웹화면으로는 안 되고, Cowork·Claude Code 또는 도구 호출을 지원하는 API로 구현

하이브리드로 질문하기 — 프롬프트 예시

💬 Cowork에서 (요지 CSV + 전문 폴더가 연동된 상태) 
연동 폴더에 판결 요지 CSV(347건)와 판결문 전문 파일들(rulings_md/)이 있어.
질문: 동료 직원들의 따돌림에 대해 손해배상이 인정된 사건과 기각된 사건의
갈림길은 무엇이었나?

먼저 요지 전체를 훑어서 관련 사건을 고르고, 고른 사건은 반드시
전문 파일을 읽은 다음, 전문을 근거로 사건번호와 판시 대목을
인용해서 답해줘. 요지만 보고 답하지 마.
사실 이렇게 지시하지 않아도 됩니다 (대체로) — Cowork·Claude Code는 과제의 성질에 따라 기본적으로 이렇게 동작합니다: 질문이 코퍼스 전반에 걸치면 목록·요지부터 훑고, 정밀한 근거가 필요해지면 해당 파일을 스스로 열어 읽습니다. 다만 가끔 요지만 보고 요약 수준으로 답하고 마는 경우가 있는데, 답변에 전문 인용이 없다면 그때 위 프롬프트처럼 "고른 사건은 반드시 전문을 읽고 답하라"고 명시적으로 지시하면 됩니다. 지시는 기본 동작을 만드는 것이 아니라 보장하는 장치입니다.
세 구조의 자리 — RAG는 대규모·서비스용, Long Context는 소규모·전체 조망용, 하이브리드는 그 사이 — "요지는 다 보되 전문은 골라 읽어야 하는" 연구 작업에 특히 잘 맞습니다. 코퍼스가 커져 요지조차 컨텍스트에 안 들어가게 되면, 그때 요지 훑기를 임베딩 검색으로 바꾸는 것이 자연스러운 진로입니다. 그리고 이 하이브리드 절차를 매번 프롬프트로 다시 쓰지 않도록 파일(스킬)로 저장하는 방법은 4주차에서 다룹니다.
4

마무리 체크리스트

  • Long Context는 "통째로 싣기" — 수만 토큰 이내 혼자 쓰는 분석이면 최선의 단순함
  • Long Context 사용 전: 자료 토큰 수 추정 → 모델 컨텍스트 창 확인 (모델마다 3.2만~100만 토큰으로 천차만별)
  • 하이브리드: 요지는 통째로(목차), 전문은 도구로 골라 읽기 — Cowork·Claude Code가 일하는 방식
