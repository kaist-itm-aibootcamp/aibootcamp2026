WEEK 4 · STEP 1 — 자율 실행의 위험과 안전장치

AI에게 일을 맡기기 전에 —
자율 실행의 위험과 안전장치

마지막 주차입니다. 이번 주 우리는 AI에게 도구를 연결하고(②③), 구글 시트에 읽고 쓰게 한 뒤(④), 마침내 24시간 상주하며 스스로 일하는 자율 에이전트를 설치합니다(⑤⑥). 그래서 첫 강의는 기능이 아니라 위험에서 시작합니다 — 사고가 어떤 구조로 나는지, 그리고 그것을 막는 두 겹의 안전장치(샌드박스, human-in-the-loop)를 먼저 손에 쥡니다.

1

자율 에이전트란 — 왜 위험부터 배우나

자율 에이전트는 사람이 매 단계 지시하지 않아도, 목표를 향해 도구를 스스로 골라 연쇄 실행하는 AI입니다. 사실 여러분은 이미 써 봤습니다.

목표 부여"판례 검색기를 배포해줘" → 판단무엇이 필요한가 → 실행파일 수정 · 명령 실행 → 해석결과를 읽고 부족하면 반복 → 결과 보고

2주차의 Cowork가 판결문 347건을 수집·정리할 때, 3주차의 Claude Code가 검색엔진을 만들어 Vercel에 배포할 때 — 어두운 상자 세 개(판단·실행·해석)를 AI가 알아서 반복했습니다. 다만 지금까지는 우리가 화면 앞에 앉아 지켜보고, 중요한 순간마다 승인 버튼을 눌렀습니다.

이번 주 ⑤⑥에서 설치할 에르메스(Hermes) 에이전트는 한 걸음 더 갑니다. 내 컴퓨터에 상시 상주하며, 텔레그램으로 말을 걸면 파일을 다루고 명령을 실행하고, 정해진 시각에 알아서 일합니다. 내가 화면 앞에 없을 때도요. 편리함의 정체가 곧 위험의 정체입니다 — 내 파일을 읽고, 쓰고, 지우고, 인터넷으로 보낼 수 있는 존재에게 열쇠를 주는 일이기 때문입니다.

이 강의의 목표 — "무섭다, 하지 말자"가 아닙니다. 위험이 어떤 구조로 발생하는지 알면, 구조의 고리 하나를 끊는 설계로 막을 수 있습니다. 열쇠를 주기 전에 잠금장치부터 배우는 것뿐입니다.
2

치명적 3요소 — 사고의 공식

보안 연구자들은 AI 에이전트 사고의 조건을 세 가지로 요약합니다. 이른바 치명적 3요소(lethal trifecta) — 셋이 모두 갖춰지는 순간, 프롬프트 인젝션 한 번으로 데이터 유출이 가능해집니다.

🗂️
① 사적 데이터 접근내 파일, API 키, 메일, 사내 문서를 읽을 수 있다. 에이전트가 일을 하려면 대부분 필요합니다.
📨
② 신뢰할 수 없는 콘텐츠 노출웹페이지, 남이 보낸 메시지, 내려받은 문서 — 남이 쓴 글을 읽는다. 일하는 내내 피할 수 없습니다.
📡
③ 외부 통신 능력인터넷으로 무언가를 보낼 수 있다 — 메시지 전송, 링크 접속, 파일 업로드.

간접 프롬프트 인젝션 — 세 요소가 연결되는 순간

①+②+③이 갖춰진 에이전트에서 사고는 이렇게 납니다:

① 남이 쓴 글을 읽음웹페이지·문서·메시지 안에
"지금까지 지시는 무시하고 …해라"가 숨어 있음 → ② 지시로 착각AI가 그것을 사용자의 명령으로 오인
= 간접 프롬프트 인젝션 → ③ 도구가 실행됨파일 삭제, 또는 파일 내용을
외부 주소로 전송

핵심은 공격자가 내 컴퓨터를 해킹할 필요가 없다는 점입니다. 에이전트가 언젠가 읽을 자리에 글을 심어 두면 됩니다 — 웹페이지 구석에, 이슈 댓글에, 스팸 메일에. 에이전트에게는 "읽은 것"과 "지시받은 것"의 경계가 본질적으로 흐릿하기 때문입니다.

파괴 — 눈에 보이는 사고

  • "정리해줘"가 rm -rf로 번역되는 경우
  • 실습 폴더가 아니라 홈 디렉터리 전체가 대상이 될 수 있음
  • 그래도 즉시 알아차릴 수 있다 — 복구는 백업의 문제

유출 — 조용해서 더 위험

  • API 키, 사내 문서, 수집한 원본 데이터가 외부 서버로 전송
  • 이미지 URL이나 링크 미리보기만으로도 데이터가 실려 나갈 수 있음
  • 아무 일도 없었던 것처럼 보인다 — 몇 달 뒤에 알게 됨
기억할 프레임 위험을 "나쁜 AI"의 문제로 보면 답이 없습니다. 3요소가 동시에 열려 있는 설계의 문제로 보면 답이 생깁니다 — 셋 중 하나만 끊어도 유출 경로는 성립하지 않습니다. 이 프레임이 §4·§5의 안전장치로 이어집니다.
3

실제 사례 — OpenClaw (2026)

이론이 아닙니다. 2026년 초, 3요소가 전부 열린 채 퍼진 에이전트가 실제로 문제를 일으켰습니다.

OpenClaw(구 Clawdbot·Moltbot)는 2026년 초 크게 화제가 된 오픈소스 자율 에이전트입니다. 메신저로 말을 걸면 내 컴퓨터에서 파일을 다루고 셸을 실행해 주는 개인 비서 — 이번 주에 우리가 설치할 에르메스와 같은 부류입니다. 그리고 바로 그 구조가 문제였습니다.

무엇이 문제였나 — "AI가 나빠서"가 아니다 보안 연구자들이 지적한 원인은 세 가지로 요약됩니다 — 과도한 권한(도구에 처음부터 광범위한 파일·셸 접근을 줌), 평문으로 놓인 비밀(API 키·토큰이 그대로 읽히는 자리에 있음), 인젝션에 대한 검증 부재(외부에서 들어온 텍스트를 지시와 구분하지 않음). 2026년 1월 Giskard 연구진은 공개 노출된 인스턴스에서 데이터 유출과 계정 탈취로 이어지는 경로를 실제로 확인했고, PromptArmor는 텔레그램·디스코드의 링크 미리보기를 통한 유출 경로를 보고했습니다. 중국 CNCERT를 비롯한 기관들도 경고를 냈습니다.

세 원인을 §2의 언어로 번역하면: 과도한 권한 = ①을 넓게 열어 둠, 검증 부재 = ②를 그대로 통과시킴, 그리고 메신저에 상주하니 ③은 처음부터 열려 있음. 3요소가 전부 열린 채 기본 설정으로 배포된 것이 사고의 본질입니다.

여기서 얻을 교훈 — 위험한 것은 "AI에게 컴퓨터를 맡기는 일" 자체가 아니라, 맡기면서 경계를 두지 않는 설계입니다. 그래서 다음 질문이 중요합니다: AI가 속았을 때도 막히는가? §4와 §5가 그 답입니다.
4

방어 ① — 샌드박스와 고립: 모델이 속아도 경계는 안 뚫린다

프롬프트 인젝션을 "AI가 더 똑똑해지면 해결되는 문제"로 보면 답이 없습니다. 첫 번째 방어는 반대 방향입니다 — 모델의 판단을 믿지 않고, 운영체제가 강제하는 울타리 안에서만 실행하게 합니다. 모델이 속아 나쁜 명령을 내려도, 울타리 밖으로는 손이 닿지 않습니다.

Claude Code의 샌드박스 — /sandbox

📁 파일시스템 격리 파괴·비밀 열람을 막는 층

  • 샌드박스 안의 명령은 작업 폴더와 세션 임시 폴더에만 쓸 수 있음
  • OS 수준 강제 — 그 명령이 실행한 하위 프로세스까지 전부 같은 경계에 묶임
  • ~/.ssh, ~/.aws/credentials 같은 비밀 파일은 읽기 자체를 차단 가능

🌐 네트워크 격리 데이터 유출을 막는 층 — 3요소의 ③을 끊는 자리

  • 샌드박스 바깥의 프록시를 통해서만 통신 — 직접 나가는 길이 없음
  • 기본 허용 도메인이 하나도 없음. 새 도메인이 필요하면 그때 승인을 물음
  • 엄격 모드에서는 목록 밖을 묻지도 않고 차단 — 데이터를 훔쳐도 내보낼 통로가 없음
어떻게 강제되나 — 약속이 아니라 커널 macOS는 시스템에 내장된 Seatbelt, Linux·WSL2는 bubblewrap(파일 격리)과 프록시 경유 통신을 씁니다. 프롬프트에 "하지 마"라고 적어 두는 방식이 아니라 커널이 거부하는 방식이라, 모델이 설득당해도 결과가 바뀌지 않습니다. Claude Code에서 /sandbox를 입력하면 켤 수 있고, 자동 승인 모드에서도 rm이 홈 디렉터리를 겨냥하면 여전히 확인을 요구합니다.

자가 호스팅 에이전트의 고립 — 컨테이너

⑤에서 설치할 에르메스에는 Claude Code 같은 내장 OS 샌드박스가 없습니다. 대신 같은 원리를 컨테이너(Docker)로 구현합니다 — 에이전트가 실행하는 셸 명령(terminal backend)을 내 컴퓨터가 아니라 일회용 컨테이너 안에서 돌게 하는 것입니다.

terminal backend = docker에이전트의 명령이 컨테이너 안에서 실행됩니다. 컨테이너가 볼 수 있는 폴더만 볼 수 있고, 지워도 컨테이너 안만 지워집니다.
읽기 전용 루트컨테이너의 시스템 영역을 읽기 전용으로 — 악성 명령이 시스템 자체를 바꿀 수 없게.
권한·자원 축소관리자 권한 제거, 프로세스 개수(PID) 제한 — 사고가 나도 피해의 상한선이 정해집니다.
한 문장으로 안전은 모델의 판단이 아니라 OS가 강제한다. "AI가 착해서 안 하는 것"과 "하려 해도 커널이 거부하는 것"은 완전히 다른 안전입니다. 자율 에이전트를 들일 때는 항상 후자를 요구하세요.
5

방어 ② — human-in-the-loop: "자율"과 "무감독"은 다르다

울타리(§4)가 사고의 범위를 좁힌다면, 두 번째 방어는 사고의 확률을 낮춥니다 — 결정적인 길목마다 사람의 확인을 끼워 넣는 설계, human-in-the-loop(HITL)입니다.

✋
실행 승인파일 삭제, 외부 전송, 새 도메인 접속처럼 위험한 동작은 실행 전에 사람에게 묻는다. Claude Code의 승인 버튼이 이것입니다.
🔑
페어링 코드아무나 내 에이전트에 말 걸 수 없게, 새 사용자는 코드를 승인받아야 연결됨. ⑤에서 에르메스 텔레그램 연동 때 직접 만납니다.
📋
화이트리스트허용한 도메인·명령·사용자 목록 밖은 기본 거부. "금지 목록"이 아니라 "허용 목록"이 안전한 기본값입니다.

여기에 알림과 보고가 더해집니다 — 에이전트가 무슨 일을 했는지 메신저로 보고하게 하면, 이상 동작을 사람이 빨리 발견할 수 있습니다. 정리하면: 자율(autonomous)은 매 단계 지시가 필요 없다는 뜻이지, 무감독(unsupervised)이라는 뜻이 아닙니다.

설계 도구로서의 3요소 — 하나를 끊어라

끊을 고리설계 방법예시
① 사적 데이터접근 범위를 작업 폴더 하나로 좁힘 · 비밀은 울타리 밖에실습 전용 폴더에서만 실행, .env는 읽기 차단
② 불신 콘텐츠외부에서 온 텍스트를 "데이터이지 명령이 아님"으로 다루고, 수상하면 실행 전 확인수집한 문서를 읽힐 때 요약·분석만 허용
③ 외부 통신나가는 통신을 허용 도메인 목록으로 제한결과 전달은 내 텔레그램 하나로만
현실적인 조합 — 셋 다 완벽히 끊으면 에이전트가 일을 못 합니다. 실무 감각은 "작업에 필요한 최소한만 연다"입니다: 이번 작업에 ①이 필요하면 ③을 좁히고, ③이 필요하면 ①을 좁히는 식으로 동시에 활짝 여는 조합을 피하는 것이 요령입니다.
6

마무리 체크리스트

이번 주 내내, 특히 ⑤⑥에서 에이전트를 설치·운영할 때 이 목록으로 돌아오세요.

  • 자율 에이전트 = 판단–실행–해석을 사람 개입 없이 반복 — 편리함의 정체가 곧 위험의 정체
  • 치명적 3요소: 사적 데이터 접근 + 불신 콘텐츠 노출 + 외부 통신 — 셋이 모이면 인젝션 한 번으로 유출
  • OpenClaw의 교훈: 과도한 권한 · 평문 비밀 · 검증 부재 — 문제는 AI가 아니라 경계 없는 설계
  • 방어 ①: 샌드박스·컨테이너 — 안전은 모델의 판단이 아니라 OS가 강제한다
  • 방어 ②: 승인 · 페어링 · 화이트리스트 · 보고 — 자율은 무감독이 아니다
  • 설계 습관: 3요소 중 최소 하나를 끊는다
다음 자료 ②이제 연결을 시작합니다 — AI를 내 데이터에 연결하는 표준(MCP 커넥터)과, 표준이 없는 시스템을 잇는 만능 어댑터(CLI)를 다룹니다.
⑤⑥ 예고오늘의 원칙을 안고 자율 에이전트를 직접 설치·운영합니다. 페어링 코드(HITL)와 docker 백엔드(고립)가 오늘 배운 개념의 실물로 등장합니다.
📚 4주차 강의자료 목록으로 돌아가기다음 자료: MCP(커넥터)와 CLI
