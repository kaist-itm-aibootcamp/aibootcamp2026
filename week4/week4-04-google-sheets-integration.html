WEEK 4 · STEP 4 — 구글 시트 연동

구글 시트 연동 —
읽기 전용에서 서비스 계정까지

②의 커넥터가 "대화 안의 연결"이었다면, 이번에는 내 앱이 직접 시트를 읽고 쓰는 연결입니다. 가장 쉬운 길(공개 + 읽기 = 백엔드 없이)부터, 정식 출입구(Sheets API + 서비스 계정)를 지나, 실무에서 바로 써먹는 활용사례(팀 현황판)까지 — 시트 연동의 전체 지도를 한 편에 담았습니다. 판단 기준은 하나입니다: 숨길 것이 있는가.

1

읽기 전용 — "웹에 게시"로 백엔드 없이

먼저 가장 단순한 경우: 데이터가 공개여도 괜찮고, 읽기만 하면 되는 경우입니다. 놀랍게도 이때는 백엔드가 전혀 필요 없습니다. 아래 데모를 클릭해 열어 보세요 — 구글 시트 하나가 실시간 대시보드가 된 모습입니다.

🔍 클릭해서 크게 보기
포트폴리오 대시보드 (동작하는 데모)

구글 시트의 보유 종목 표 → 평가액·수익률·비중 차트. 시트를 고치면 화면이 따라 바뀝니다. 데모는 시세 변동을 시뮬레이션하며, 데이터는 전부 가상입니다.

구글 시트내가 편집하는 원본 → "웹에 게시"파일 → 공유 → 웹에 게시 → CSV
구글이 공개 CSV 주소를 발급 → 브라우저가 직접 fetch30초마다 다시 읽음 (폴링) → 화면 갱신

구조가 이렇게 단순한 이유: 숨길 것이 없기 때문입니다. 시트 메뉴의 파일 → 공유 → 웹에 게시에서 형식을 CSV로 고르면 …/pub?output=csv 형태의 공개 주소가 생기고, 페이지의 자바스크립트가 그 주소를 일정 간격으로 다시 읽어(폴링) 화면을 갱신합니다. 서버 없이 정적 호스팅(GitHub Pages — 1주차 방식 그대로)에 올리면 끝. 조별과제 현황, 독서 기록, 동아리 회비 장부 — 시트로 관리하는 모든 것이 이런 대시보드가 될 수 있습니다.

전제 조건 — "게시"는 공개라는 뜻이다 게시 URL은 주소를 아는 누구나 열 수 있습니다. 로그인도 권한 확인도 없습니다. 그리고 게시는 내보내기 전용이라 쓰기는 불가능하고, 비공개 시트는 애초에 게시할 수 없습니다. 즉 이 방식의 적용 범위는 정확히 "공개 + 읽기"까지 — 그 밖은 전부 §2부터의 정식 출입구가 필요합니다.
2

정식 출입구 — Sheets API가 필요한 순간

§1의 공식이 깨지는 순간은 금방 옵니다 — 비공개 시트를 읽어야 하거나, 시트에 써야 할 때입니다.

📝
세미나 신청 페이지방문자가 이름·이메일을 제출하면 신청자 명단 시트에 한 행 추가 — 쓰기 발생, 명단은 비공개.
📊
팀 진행률 업데이트팀원이 대시보드에서 자기 진행률을 고치면 시트의 해당 셀이 바뀜. (§5에서 시연)
💬
챗봇 문답 이력 기록3주차에 만든 판결문 챗봇의 질문·답변이 시트에 차곡차곡 쌓이는 구조 — 그때 쓴 것이 바로 오늘의 방식입니다.

공통 구조: 여러 사람이 쓰는 웹 화면 ↔ 내가 관리하는 시트 하나. 시트가 사실상 데이터베이스 역할을 합니다. Supabase 같은 진짜 DB보다 훨씬 단순하지만, 눈으로 보고 손으로 고칠 수 있어 MVP 단계에서는 오히려 강력합니다.

사람은 브라우저로 시트를 엽니다. 프로그램은 Google Sheets API라는 별도의 출입구를 씁니다 — "A2 셀 값을 읽어라", "맨 아래 행에 이 값들을 추가하라" 같은 요청을 보내면 구글이 수행해 줍니다. 단, 이 출입구에는 문지기가 있습니다. 모든 요청은 "너는 누구이며, 이 시트에 대한 권한이 있는가"를 증명해야 합니다. 사람이라면 구글 로그인으로 증명하겠지만 — 프로그램은 로그인 화면을 통과할 수 없습니다.

3

서비스 계정 — 프로그램에게 주는 신분증

그래서 구글은 프로그램 전용 구글 계정을 만들 수 있게 해 두었습니다. 이것이 서비스 계정(service account)입니다.

정체사람이 아닌 프로그램이 쓰는 구글 계정. 내앱@프로젝트.iam.gserviceaccount.com 형태의 이메일 주소를 갖습니다.
로그인 방법비밀번호 대신 JSON 키 파일. 이 파일을 가진 프로그램이 곧 그 계정입니다.
권한 부여놀랍도록 직관적입니다 — 시트의 공유 버튼으로 서비스 계정의 이메일을 초대하면 끝. 사람 동료를 초대하듯, 뷰어(읽기)나 편집자(쓰기) 권한을 고를 수 있습니다.
범위공유받은 그 시트만 접근 가능. 내 드라이브 전체가 열리는 것이 아닙니다. 필요한 만큼만 주는 것 — ①에서 배운 최소 권한 원칙 그대로입니다.
내 프로그램JSON 키로 신원 증명 → Sheets API"이 계정이 이 시트 권한이 있는가?" → 공유받은 시트읽기 / 쓰기
②의 커넥터와 비교: 커넥터는 내가 로그인해 내 계정 권한을 AI에게 빌려주는 방식(토큰), 서비스 계정은 프로그램 자신의 계정을 만들어 시트에 초대하는 방식입니다. 사람이 매번 로그인할 수 없는 "무인 서비스"에는 서비스 계정이 표준입니다.
4

실습 — 열쇠 발급과 보관 장소

발급은 구글 클라우드(GCP) 콘솔에서 합니다. 절차가 길어 보이지만 전부 클릭이며, 비용은 들지 않습니다. 수업에서는 강사가 미리 발급해 둔 실습용 키를 나눠 드립니다 — 아래는 각자 자기 열쇠를 만들 때(자율 과제) 따라가는 지도입니다.

1 GCP 프로젝트 만들기

console.cloud.google.com 접속(구글 계정으로) → 상단 프로젝트 선택 → 새 프로젝트 → 이름(예: sheet-mvp) 입력 → 만들기.

2 Sheets API 켜기

검색창에 Google Sheets API 입력 → 사용(Enable). 이 프로젝트가 시트 출입구를 쓰겠다는 신고입니다.

3 서비스 계정 만들기

메뉴 → IAM 및 관리자 → 서비스 계정 → 만들기 → 이름 입력 → 나머지는 기본값으로 완료. 생성된 …@….iam.gserviceaccount.com 이메일을 복사해 둡니다.

4 JSON 키 다운로드

만든 서비스 계정 클릭 → 키(Keys) 탭 → 키 추가 → 새 키 만들기 → JSON. 키 파일이 내려받아집니다. 이 파일이 곧 계정입니다 — 메신저·메일로 보내거나 GitHub에 올리면 안 됩니다.

5 시트를 서비스 계정에 공유

데이터 시트를 열고 공유 → 3단계의 이메일 붙여넣기 → 권한 선택: 읽기만 필요하면 뷰어, 쓰기까지 필요하면 편집자 → 보내기.

결정적 질문 — 이 열쇠를 어디에 두나

❌ 브라우저(프런트엔드)에 두면

페이지를 여는 모든 방문자가 개발자도구로 키를 꺼낼 수 있습니다. 편집자 권한 키라면 누구든 내 시트를 통째로 지우거나 조작할 수 있습니다. 3주차 배포에서 본 API 키 문제와 완전히 같은 구조 — 단, 이번엔 요금이 아니라 데이터 자체가 위험합니다.

✅ 서버(백엔드)에 두면

브라우저는 "이 값을 추가해 주세요"라고 부탁만 하고, 키를 든 서버리스 함수가 검증 후 대신 씁니다. 방문자는 키를 볼 방법이 없고, 서버가 허용한 동작(예: 행 추가만)만 가능합니다.

3주차의 공식, 다시 등장 비밀은 서버에, 환경변수로. 3주차에는 OpenRouter 키와 Gmail 앱 비밀번호였고, 지금은 서비스 계정 JSON 키입니다. 배포도 3주차와 같은 방법(Vercel + 환경변수)이면 됩니다. 그리고 ⑤에서 에르메스의 .env 파일을 만날 때 이 공식이 한 번 더 등장합니다.
5

활용사례 — 팀 프로젝트 현황판

이 구조를 실무에 그대로 옮긴 사례입니다. 대부분의 팀은 이미 구글 시트로 무언가를 관리하고 있습니다 — 그 시트는 그대로 두고, 보는 화면만 서비스로 만드는 것이 이 패턴입니다. 아래 데모에서 팀원을 골라 진행률을 제출해 보세요.

🔍 클릭해서 크게 보기
팀 프로젝트 현황판 (동작하는 데모)

팀원별 진행률 바, 마감 임박 항목, 진행률 제출 폼. 실제 버전에서는 제출이 팀 공유 시트의 셀을 갱신합니다. 데모는 브라우저 안에서 시뮬레이션합니다.

🧾
원본은 익숙한 시트관리자는 지금까지처럼 시트에서 일정·담당을 편집합니다. 새 도구 학습 비용 0.
🖥️
보는 사람은 화면팀원·상사·회의실 TV는 잘 정리된 대시보드를 봅니다. 시트의 지저분한 수식·메모는 보이지 않습니다.
✍️
쓰는 것도 화면에서진행률처럼 자주 바뀌는 값은 화면의 폼으로 제출 → 시트의 정해진 셀만 갱신. 실수로 남의 행을 지우는 사고가 원천 차단됩니다.

쓰기의 두 유형도 여기서 구분됩니다: 접수·수집형 서비스는 행 추가(append), 현황·관리형 서비스는 셀 갱신(update). 프롬프트에 이 의도만 정확히 적으면 AI가 알맞은 API 호출을 골라 씁니다. 회사에 옮기면: 주간 실적 시트 → 팀 실적 보드, 비품 재고 시트 → 재고 현황판. "이미 시트로 관리 중인 것" 목록이 곧 여러분의 서비스 후보 목록입니다.

💬 완성 프롬프트 (자율 실습) 
구글 시트를 데이터베이스로 쓰는 "팀 프로젝트 현황판" 웹앱을 만들어줘. Vercel에 배포할 거야.

시트 구성 (1행은 머리글): A=이름, B=담당 파트, C=진행률(0~100), D=마감일(YYYY-MM-DD)

기능:
1. /api/read : 전체 행을 JSON으로 반환.
2. 화면 왼쪽: 팀원별 진행률 바(퍼센트 표시), 그 아래 마감일 오름차순의
   "마감 임박" 목록. 마감 3일 이내는 빨간 배지, 7일 이내는 주황 배지.
3. 화면 오른쪽: "내 진행률 업데이트" 폼 — 팀원 선택 + 0~100 슬라이더 + 제출.
4. /api/write : 선택한 팀원의 C열(진행률)만 갱신. 값이 0~100 범위 밖이거나
   명단에 없는 이름이면 거부. 다른 열은 절대 수정하지 않게.
5. 60초 폴링으로 자동 갱신. 반응형.
6. 인증은 환경변수 GOOGLE_SERVICE_ACCOUNT_KEY와 SHEET_ID 사용, 키는 코드에 넣지 마.
7. 파일 변경까지만 하고 git commit/push는 하지 마.
남는 문제 — 이 주소를 아는 사람은 누구나 서비스 계정 키는 안전하게 숨겼지만, 화면과 폼 자체는 전체 공개입니다. 조별과제라면 무방해도 회사 실적 보드라면 문이 필요합니다 — 3주차에 배운 이메일 인증코드 방식이 정확히 그 문입니다. 필요하면 3주차 자료(인증·접근 통제)를 다시 펴 보세요.
6

마무리

  • 공개 + 읽기 = "웹에 게시" CSV + 폴링 — 백엔드 불필요, 단 게시는 공개라는 뜻
  • 비공개 또는 쓰기 = Sheets API + 서비스 계정 — 프로그램용 구글 계정을 시트에 초대
  • JSON 키가 곧 계정 — 비밀은 서버에, 환경변수로
  • append(접수·수집)와 update(현황·관리)를 구분해 프롬프트에 명시
  • 시트는 그대로, 화면만 서비스로 — 이미 시트로 관리 중인 것이 서비스 후보
다음 자료 ⑤ — 에르메스 에이전트 ①연결의 도구함(MCP·CLI·시트)이 갖춰졌습니다. 이제 이 도구들을 쥐고 24시간 상주하며 스스로 일하는 자율 에이전트를 직접 설치합니다 — 텔레그램·OpenRouter 연동까지.
자율 실습§4 절차로 내 서비스 계정을 발급하고, §5 프롬프트를 우리 팀 시트에 맞게 고쳐 현황판을 배포해 보세요. 실습용 공용 키는 수업 후 회수(비활성화)됩니다.
